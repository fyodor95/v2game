# Национальные провинции великих держав

Статус: реализация и квалификация, функция ещё не установлена в основную игру.
Полный план — [great-power-culture-cores.md](../../../docs/plans/great-power-culture-cores.md).

`calculation.h` вычисляет отсортированные пары корок из снимка мира только по
основным культурам держав. При ничьей учитываются все крупнейшие культуры;
совпадение признанной культуры права на новую корку не даёт.
`scheduler.h` содержит чистый планировщик и фиксированный кодек глобальных флагов.
`test.cmd` собирает и запускает оба набора нативных тестов MSVC Win32.

Независимый oracle:

```powershell
python -m unittest discover -s tools/creatinecore/gpc -p test_save_oracle.py
python tools/creatinecore/gpc/save_oracle.py --save <копия.v2> --game-root <игровая-копия> --gp ENG FRA --output <новый-отчёт.json>
```

Теги GP должны быть независимо подтверждены в игре. Парсер не угадывает их по
рейтингу или порядку стран. Ничьи обрабатываются по всем крупнейшим культурам.
Это диагностический инструмент, не редактор сохранений.

## Квалификационный плагин

`build_probe.cmd` собирает `.work/gpc-build/gpc_qualification.dll`.
Копировать его только в `dll_Submods` отдельной игровой среды вместе с нативным
CLI-мостом. `qualification_events.txt` копируется в её `events`.
Плагин отказывается загружаться без `VIC2_TEST_SESSION`.

По умолчанию журналирует дневную фазу, читает GP/технологии и проверяет MTTH
трёх тестовых событий. Переменная `VIC2_GPC_PROBE_STATE=1` дополнительно разрешает
квалификацию seed и запись состояния через штатные глобальные флаги.
`VIC2_GPC_PROBE_TARGET=658:ENG` вместе с
`VIC2_GPC_MUTATION_ALLOWED=ISOLATED_SINGLE_PLAYER` разрешает тестовую выдачу одной
корки в первых двух дневных callback. Вторая попытка проверяет отсутствие дубля.
Эти режимы предназначены исключительно для изолированной одиночной игры.

Плагин не является производственной реализацией: нет включённого расчёта/выдачи
всего мира, доставки уведомления и подтверждённой сетевой синхронизации.
Логи установки hook не доказывают завершения этих проверок.

## Диагностический барьер производственного runtime

`runtime_status.h` задаёт C ABI v1: `V2GpcRuntimeStatus` из двенадцати `uint32_t`
(48 байт). Символ `V2Gpc_GetRuntimeStatus` экспортируется без декорирования имени;
его можно найти через `GetProcAddress` в уже загруженной DLL механики.

```cpp
int __cdecl V2Gpc_GetRuntimeStatus(V2GpcRuntimeStatus* output, uint32_t output_size);
```

При `output_size >= 48` и доступном выходном буфере возвращает 1 и целый снимок.
При 0 использовать буфер нельзя. Клиент проверяет `size`, `version` и boolean
поля как `uint32_t` 0/1. Getter копирует только кэш под короткой блокировкой:
не читает world/флаги, не вызывает движок, не расходует RNG и не запускает проход.
Блокировка не удерживается во время работы движка или журналирования.

| Поле | Значение |
|---|---|
| `size`, `version` | Размер структуры и версия ABI |
| `enabled` | Прочитанная настройка включения механики |
| `failed` | Необратимая ошибка установки/обработки в текущем процессе |
| `busy` | Один или несколько незавершённых `OnDay`, включая вложенный вызов |
| `has_schedule` | Есть успешно прочитанное/инициализированное завершённое расписание |
| `last_callback_raw_date` | Последняя прочитанная сырая дата callback, даже если последующая обработка завершилась ошибкой |
| `last_completed_raw_date` | Последняя дата, для которой обработка успешно завершилась |
| `pass`, `rng`, `state_digest` | Номер прохода, RNG и checksum последнего завершённого состояния расписания |
| `core_digest` | Кэш digest корок последнего фактического полного прохода в этом процессе |

Начальные даты и digest равны нулю, `has_schedule=0`. Нулевая дата не является
игровой датой. После первого callback инициализация может уже иметь
`has_schedule=1`, `pass=0`: это обычное ожидание первой попытки, а не отсутствие
расписания. Выключенная DLL отвечает `enabled=0`, `busy=0`, с нулевыми датами:
дневной hook для неё не ставится. Отсутствующая DLL/символ — отдельное состояние
`unavailable` на стороне CLI, его нельзя представлять как `enabled=0`.

`busy` выставляется в самом начале `OnDay` и сбрасывается RAII при каждом выходе.
Завершённая дата публикуется только после успешной записи флагов либо успешной
проверки дублирующего callback той же даты. Непроходной день тоже завершается:
отсутствие выдачи не означает отсутствие барьера. Ошибка оставляет прежние
завершённые значения, выставляет `failed=1` и запрещает дальнейшую обработку,
как и до добавления диагностики. Повторный callback не создаёт лишнего draw RNG.

Для сравнения двух участников контроллер сначала подтверждает общую паузу и
равные сырые даты мира, затем требует у включённого модуля `failed=0`, `busy=0`,
`has_schedule=1`, `last_callback_raw_date == last_completed_raw_date == world_date`.
Только после этого сравниваются `pass/rng/state_digest`. При исходной сборке
без модуля или выключенной механике это другой сценарий, для которого барьер
активного расписания неприменим.

`core_digest` не является полным хешем мира, вычисляемым по запросу. Он обновляется
после фактической выдачи и успешной фиксации прохода, а между проходами сохраняется.
До первого полного прохода в этом процессе он равен нулю; загрузка сохранённого
расписания сама по себе не вычисляет digest корок. Поэтому доказательство корок
опирается на новый подтверждённый проход и независимый oracle/сохранение.
После загрузки другой кампании в том же процессе старый кэш до нового callback
не служит барьером новой кампании; одного совпадения календарной даты недостаточно.
