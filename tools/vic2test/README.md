# Нативные тесты Victoria II

Экспериментальный плагин CreatineCore и клиент на Python 3.12. Поддерживается
только EXE 3.04 с SHA-256 `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`.
Плагин активируется только при переменной `VIC2_TEST_SESSION`, которую задаёт клиент.
Обычная игра не открывает управляющий канал.

Сборка: `tools\vic2test\build.cmd` (MSVC 2026, x86). Результат находится
в `.build\vic2_test_bridge.dll`. Его помещают в `z_CreatineCore\dll_Submods`
только тестовой копии. Пока квалификация на настоящем движке не завершена,
плагин нельзя считать готовым для обычных кампаний.

```powershell
python tools/vic2test/cli.py prepare --destination .work/test-run --save "D:/Documents/Paradox Interactive/Victoria II/save games/isolation_baseline.v2"
# Установить в тестовую копию ядро, конфигурацию и собранный тестовый плагин.
python tools/vic2test/cli.py start --environment .work/test-run --save isolation_baseline.v2 --hidden
python tools/vic2test/cli.py status --environment .work/test-run
python tools/vic2test/cli.py decision check --environment .work/test-run --tag HAW --id example_decision
python tools/vic2test/cli.py snapshot --environment .work/test-run --tag HAW
python tools/vic2test/cli.py advance --environment .work/test-run --days 1
python tools/vic2test/cli.py stop --environment .work/test-run
```

Подготовка копирует файлы без жёстких ссылок, перенаправляет `userdir.txt`, выключает
автосохранение. Сам факт записи перенаправления ещё не доказывает его применение
игрой: перед тестированием нужно проверить расположение новых логов/настроек.
При подготовке и перед каждым запуском все четыре уровня звука тестовой копии
устанавливаются в ноль: master, music, sound FX и ambient. Основной профиль
пользователя не меняется. Перед новым запуском старые журналы сохраняются в
`log-history/<session-token>`; это предотвращает смешивание с предыдущими PID.

Команды движка выполняются из перехвата штатного `PeekMessageA` на главном потоке,
в том числе при паузе. IPC-поток не разыменовывает объекты игры. `WM_NULL` будит
цикл сообщений; клики и клавиатура для нативных команд не используются.
Загрузка использует проверенные контроллеры меню и штатные сигналы движка.

Проверка решения вычисляет настоящие `potential` и `allow`. Выполнение пока
поддерживает только текущую страну игрока и ставит штатную команду в очередь.
`queued=true` не означает завершения эффектов. Требуется отдельная проверка
изменённого состояния после обработки очереди.

`event --tag HAW --id 123 --option 1` вызывает зарегистрированный обработчик
`event`, дожидается настоящего окна события и выбирает вторую опцию штатным
обработчиком движка. Это нативная операция без физических кликов и клавиатуры.
Обработчик сам создаёт действие с копией scope; немедленные эффекты повторно
не запускаются. Без `--option` окно события остаётся для обычного выбора.
Поддержка выбранной опции ограничена событиями текущей страны игрока и её провинций. В рабочем
прогоне главного агента подтверждены нативная автозагрузка, изменение условий
решения после выбранной опции события и ровно одно списание £1 при выполнении
решения. Это проверка конкретного сценария, не гарантия для всех scopes.

`save --name ccore_smoke` вызывает штатную сериализацию движка. Полный путь
ограничен пользовательским каталогом тестовой копии, существующий файл не
перезаписывается. CLI проверяет появление непустого файла и возвращает SHA-256.
Главный агент подтвердил создание `ccore_smoke.v2` (19 581 293 байта), завершение
процесса, повторную автоматическую загрузку этого файла с той же датой и прохождение
ещё одного дня. Обратной загрузки в том же процессе и произвольных снимков
флагов/модификаторов пока нет.

`check --root .` проверяет структуру скриптов и повторные идентификаторы, но
не исполняет условия. Тестовый мод `fixtures/vic2test` проверяет разницу между
немедленными эффектами, двумя выбранными опциями и одноразовым решением.

`run fixtures/smoke.json --environment .work/test-run` исполняет реальные команды
и проверяет JSON-поля. Шаг содержит `args` (аргументы CLI без `--environment`),
необязательный `expect` (поля и ожидаемые значения) и необязательный `delta`
(`field`, `from` — номер предыдущего шага с нуля, `value` — точное изменение).
Для денег проверяется целочисленный `treasury_raw`, чтобы не вводить погрешность
двоичной арифметики. Файл сценария рассчитан на свежую кампанию HAW с тестовым
модом, до выполнения события/решения.

Для провинциального события использовать `event --province 658 --id 990002 --option 1`.
Тип события проверяется по настоящему реестру движка; страна и провинция не
подменяют друг друга, неверная область даёт `E_EVENT_SCOPE` до выполнения эффектов.
Номер провинции проверяется по загруженной таблице и текущему владельцу.
Для провинциального события используется штатный `CEvent::run` с настоящим
провинциальным scope: консольный обработчик этой версии сохраняет страновую
область и не выполняет эффекты `owner` правильно. Страновые события используют
зарегистрированный обработчик консоли.
Сценарий `fixtures/province-smoke.json` проверяет обе области через `owner`,
немедленный эффект, выбранную опцию и точную прибавку £113. Все семь шагов
подтверждены на настоящем движке: immediate и опция1 установили свои флаги,
флаг опции0 отсутствовал, казна изменилась с £492.12637329 до £605.12637329.
Поддерживаются провинции текущего игрока; чужие и несуществующие цели отвергаются.

`advance` останавливает игру при достижении целевой сырой даты. В отчёте сохраняется
фактическая дата: кратность тиков и возможный переход дальше цели требуют проверки
на настоящем движке. Прогон использует штатное увеличение скорости до максимальной;
пока цель не достигнута, вызванные уведомлениями паузы снимаются. Если событие
ожидает выбора, обычный прогон останавливается с `E_EVENT_BLOCKED` и ставит игру
на паузу. Явный `--auto-events` разрешает выбор первых опций фоновых событий
только на время этого прогона; ID и число таких выборов записываются в лог.
Событие, запрошенное отдельной командой и ожидающее заданную опцию, автоматически
не выбирается: такой прогон отвергается до начала движения времени.

При подготовке тестовой копии обычные всплывающие уведомления и их паузы
выключаются в её собственном `messagetypes_custom.txt`. Это не меняет оригинальные
настройки пользователя и не заменяет выбор вариантов настоящих скриптовых событий.

При `E_NATIVE_EXCEPTION` или `E_TIMEOUT` сессию нужно завершить и запустить заново.
Весь обмен имеет ограничение по времени, включая чтение ответа. При истечении
срока синхронный I/O отменяется, а сессия помечается повреждённой. Это не отменяет
уже начатый игровой эффект; последующие игровые команды запрещены до перезапуска.
Нативное исключение также закрывает возможность дальнейшего обращения к движку.
Ожидающее выбора событие защищено от перезаписи следующим запросом; выбор опции
для страны AI явно отвергается.

Успех сохранности исходных файлов и обработки тайм-аутов проверяется командой:
`python -m unittest discover -s tools/vic2test -p test_cli.py`.

Источники контрактов: закреплённый `V2TechButton.cpp` (DecisionCull и FireDecision),
`vasalle_color.cpp` (аргументы консоли), а также Smedley
`kernel/game_state/src/runtime.cpp`, `v2_304_layout.hpp` и
`kernel/include/smedley/events/console.hpp`. Статические совпадения не заменяют
проверку поведения на работающей игре.

## Сетевая игра без физического ввода

Сетевой мост создаёт настоящую партию Victoria II: вызывает штатные callbacks
меню и передаёт команды в сетевую очередь. Мышь, клавиатура и фокус окна не
требуются. Игра остаётся обычным Windows-процессом с оконной подсистемой;
это не отдельный серверный исполняемый файл.

Подготовить **две разные** среды командой `prepare`, установить в обе одинаковое
ядро и `.build/vic2_test_bridge.dll`. Пользовательский сейв копируется, исходник
сохраняется. Для уже подготовленных сред:

```powershell
python tools/vic2test/mp_driver.py --host .work/gpc-mp-host --client .work/gpc-mp-client --save 1891.v2 --host-tag AUS --client-tag NGF --start --days 20 --output .work/gpc-artifacts/mp-run-new.json
```

Контроллер сравнивает файлы сборок до запуска, создаёт скрытые процессы,
открывает host/join на `127.0.0.1`, загружает сейв хоста, выбирает страны,
выполняет Play и Start. Каждая изменяющая команда отправляется один раз;
контроллер отдельно ждёт подтверждений обоих участников. После прогона он
дожидается общей паузы и одинаковой фактической даты, записывает JSON-отчёт
и завершает только созданные им процессы по удерживаемым Windows handles.
`--leave-running` оставляет их для диагностики; без `--start` используются
уже запущенные среды и их процессы автоматически не завершаются.

`--days` задаёт минимальную длительность: доставка сетевой паузы может дать
небольшой переход дальше цели, поэтому отчёт содержит фактическую дату.
`--speed` принимает внутренние уровни `0..4`. Один шаг изменения скорости
обязательно подтверждается обоими участниками перед следующим.

Низкоуровневые команды для диагностики:

```powershell
python tools/vic2test/cli.py mp lobby --environment .work/gpc-mp-host
python tools/vic2test/cli.py mp state --environment .work/gpc-mp-host
python tools/vic2test/cli.py mp pause --paused yes --environment .work/gpc-mp-host
python tools/vic2test/cli.py mp speed --level 4 --environment .work/gpc-mp-host
```

`mp state` возвращает роль, готовность сети, паузу, скорость, сырую дату,
ожидающую команду и `can_start`. `queued=true` означает постановку в очередь;
это ещё не подтверждение результата на втором участнике. Управление паузой
и скоростью разрешено только хосту в готовой сетевой кампании. Обычные
SP-команды `pause`, `advance`, `event`, `decision` и `save` в MP отвергаются.
Штатная консоль не используется для обхода этого ограничения.

Ожидание ограничено сроком. Известный отказ **до** отправки (`E_MP_BUSY`,
для Start также `E_MP_NOT_READY`) допускает повтор после ожидания. Отправленная
команда, тайм-аут IPC или неизвестный исход не допускают повторной мутации.
При повреждённой сессии требуется новый процесс.

Квалификация базового управления: скрытые host/join/load/country/Play/Start,
скорости `0→4`, снятие и постановка паузы, отдельный 20-дневный прогон с общей
конечной датой; пять проверок отказа запрещённых команд. В контрольной партии
214 дневных записей штатных сумм на каждом участнике совпали, `first_real=-`.
Это подтверждает управление стендом; приёмка нового механизма выдачи корок
в MP ведётся отдельно. Сохранение хостом также подтверждено в полном
автоматическом запуске: `--save-result mp_native_01` создал непустой `.v2`,
разобранный независимым парсером; общая пауза и дата сохранились. Перезапись
файла и сохранение клиентом отвергаются. Перехост из этого сейва со сменой
ролей прошёл: ещё четыре согласованных дня и повторное сохранение. Сетевой
выбор настоящей опции подтверждён на клиенте: его уведомление закрыто, окно
хоста оставалось открытым ещё 40 дней, все 22 прохода и сетевые суммы совпали.

`culture-cores preview`, `snapshot` и `run` сохраняют новые JSON в собственном
`userdata/gpc-debug`. Первые две команды читают данные без изменения мира;
`run` разрешён только в SP и сохраняет RNG и дату, увеличивая номер прохода.
После `advance` и перед `save` CLI дожидается завершённой GPC-фазы: остановка
календаря сама по себе ещё не означает завершение обработки дня.
Проверки API на настоящих сейвах: 1931 — 25 точных добавлений, повтор — ноль;
1841 — ноль из-за отсутствия технологии; ничья — корки для обеих культур.
`test_debug_abi.cmd` дополнительно проверяет 82 сценария C ABI без запуска игры.

`return-menu` и `load --save <имя>` предназначены для повторных загрузок в одном
SP-процессе через штатные меню. Возврат отбрасывает несохранённую тестовую партию.
Исправленный переход прошёл три смены кампаний в одном процессе
(1836 → 1931 → 1841 → 1836); новый console capture и расписание проверены
после каждой загрузки. Контракты описаны в
[отдельном отчёте](../../docs/research/gpc-sp-return-menu-contracts.md).

`culture-cores status` читает только диагностический кэш установленного модуля:
состояние обработки дня, номер прохода, RNG и контрольные суммы. Перед сохранением
контроллер ждёт завершения GPC-фазы и сравнивает состояния участников. Команда
не выдаёт корки и не расходует случайные числа. Если модуль выключен или
отсутствует, это явно указано в ответе. Контракт кэша описан в
[руководстве GPC](../creatinecore/gpc/README.md).

Контракты: [меню и загрузка](../../docs/research/gpc-mp-ui-contracts.md),
[пауза и скорость](../../docs/research/gpc-mp-control-contracts.md),
[создание лобби](../../docs/research/gpc-mp-driver-contracts.md).

При зависании до главного меню проверить собственный `userdata/logs/system.log`.
Сообщения `Failed to create a device` относятся к инициализации Direct3D до
обработки owner-thread IPC; работающий worker не доказывает готовность игры.
После доставленного запроса с истёкшим сроком не повторять команды. Сохранить
диагностику и завершить только свой процесс с подтверждённым полным путём.
Запуск без физического ввода всё равно требует исправного графического устройства.

При проверке естественного срабатывания событий ускорения MTTH недостаточно:
провинциальный скан проверяет предварительный список кандидатов, обновляемый
при смене календарного месяца. При холодной загрузке сохранения этот список
и реестр случайных провинциальных событий могут штатно оставаться пустыми до
ближайшей смены месяца. Условия, ставшие истинными после построения списка,
также могут ждать следующего обновления. Успешный `decision-check` с тем же
trigger сам по себе не подтверждает присутствие события в списке.

Провести игру через следующую смену месяца и последующую провинциальную фазу,
контролируя условия и нативные списки. Для старта 1836.1.1 в проверенном опыте
реестр заполнился на +31 день, а окно события появилось на +32 уже после
возврата `advance`: достижение raw date ещё не означает окончания обработки
дня. Для такого стенда заложен интервал до 36 дней с проверкой окна,
автоматической опции и итоговой корки в сохранении. Сам срок не гарантирует
срабатывание случайного события. Нативные адреса и контракт холодной загрузки
описаны в [контракте frontend](../../docs/research/gpc-mp-ui-contracts.md#холодная-загрузка-и-месячный-реестр-событий),
а tutorial gate и пределы вывода — в
[отчёте CoreAddingEvents](../../docs/research/chronology-core-events.md#естественные-события-месячный-список-кандидатов).

`event-check --environment .work/test-run --province 546 --id 24495` проверяет
настоящее провинциальное событие, не вызывая его. Команда разрешена только в
одиночной кампании на паузе после окончания текущего дня, для провинции игрока.
Она не ставит паузу самостоятельно, не вызывает RNG/эффекты и не обновляет кэш.
Каждый predicate получает отдельный провинциальный scope: страна `---/0`, номер
провинции в `+10`, как в естественном скане. Это отличает проверку от обёртки
того же текста в страновом `decision-check`.

В ответе `all`, `random` и `cached` содержат размер и `contains` для общего
реестра провинциальных событий, фильтрованного реестра естественных событий и
месячного списка выбранной провинции. `trigger` — текущий результат настоящего
trigger, `children` — результаты непосредственных условий в исходном порядке.
`mtth.days_fixed` — дни ×1000, `threshold` — нативный целочисленный порог из
1 000 000 с провинциальным `multiplier=2`. `tutorial=1` отключает обычный
естественный скан. Также возвращаются `triggered_only`, `fire_only_once` и
число опций. Истинный trigger при `cached.contains=false` ещё не участвует в
естественном скане; наличие в списке само по себе не доказывает выполнение.

Пока квалифицированы детерминированные условия первой корки (AND/OR/NOT,
owner/явная страна, культура, primary, exists, tag, is_core, REB, always,
any_core с единственным always), без modifiers MTTH. Другой класс, scope,
изменённая нативная сигнатура или неизвестный layout дают `E_NATIVE_LAYOUT`
до вызовов движка. `E_PAUSE_REQUIRED` и `E_DAY_BUSY` означают, что безопасная
точка для проверки ещё не достигнута. Отказ не является успешной диагностикой.
Первоначальная квалификация использовала событие24754 и провинцию546 старого
набора: четыре условия, пустые random/cache и threshold1000000. В текущей
генерации OBO —24495; новые условия и естественное срабатывание проверены
отдельно. После перегенерации брать ID из свежего manifest, а не переносить
номер из прежнего отчёта. Произвольные другие события не квалифицированы.
Отрицательные пути также проверены движком: чужая провинция — `E_PLAYER_ONLY`,
страновое событие3997301 — `E_EVENT_SCOPE`, отсутствующее событие — `E_NOT_FOUND`.
В отдельной свежей GUI-кампании [естественное срабатывание подтверждено](../../docs/research/chronology-core-events.md#подтверждённое-естественное-срабатывание):
OBO присутствовал в cache, trigger сменился с true на false, лог автоматического
выбора содержит24754, а сохранение — единственную OBO-корку в провинции546.

SP `load-save` использует настоящую строку сохранения из `bookmarks_list` и
штатный callback `00777DB0`, как квалифицированный сетевой путь выбора сейва.
Callback ставит `CClearBookmark` в очередь, меняет выбор строки и вызывает
обычный механизм загрузки `00778080`. Прежняя запись имени прямо в `frontend+590`
и флага `+5BC` обходила эти действия. Тип строки `CSavegameItem`
проверяется по vtable `00E15190`; отсутствующая либо неоднозначная строка
отклоняется до выбора. `frontend-status.save_loaded` теперь требует `5BD=1`,
`5BC=0` и доступную `play_button` (нативный getter `vt+B0`, состояние3 означает
недоступность). `play` проверяет те же условия и посылает обычный Signal.
Callback воспроизводит полный штатный обработчик выбора; он не устраняет
пустой начальный кэш. Опыт после этого исправления сохранил random/cache=0,
а следующий опыт подтвердил их штатное обновление при смене месяца. Ручного
построения event cache, вызова init или дополнительного hook Initialize здесь
нет. Полную автоматическую проверку корки отличать от наблюдения обновлённого
реестра и открытого окна события.

`status` дополнительно возвращает `all_province_events` и
`random_province_events` — количества записей в проверенных реестрах менеджера.
В меню или при неизвестном layout эти значения равны `null`. Подсчёт не
вычисляет trigger и не меняет списки; он одинаково подходит старому и новому
набору событий. Сразу после холодной загрузки `random_province_events=0`
допустимо. Перед измерениями CoreAddingEvents после каждой загрузки требуется
одинаковый прогрев старого и нового набора через смену месяца, затем проверка
`random_province_events > 0`; время прогрева учитывать отдельно от измеряемого
интервала. Положительное число подтверждает заполнение общего реестра, но не
наличие конкретного события в списке провинции: для этого нужен
`event-check.cached.contains`. `null` не равен пустому квалифицированному
реестру. Существование `CInGameIdler` само по себе не доказывает окончание его
штатной инициализации, а начальный нулевой реестр не доказывает её дефект.

Для новых первых корок расширен `event-check-province`: квалифицированы
`pop_majority_religion`, страновая ветка `civilized` и `country_religion`
из текущей CreatineCore. Последняя проверяется по точному клону vtable и полным
телам двух функций с учётом ASLR; при другой компиляции требуется повторное
ревью. Справочник религий должен быть уже заполнен, включая служебный
`noreligion` в слоте0: диагностика не запускает ленивую инициализацию.
Реальные положительная и три отрицательные проверки описаны в
[отчёте культур и религий](../../docs/research/culture-religion.md).

MP-команды `mp-events` и `mp-option` поддерживают естественные провинциальные
окна с country-scope `---/0` и проверяют текущего владельца провинции. В ответах
возвращаются `scope` (`country`/`province`) и `province` (0 для страны).
Выбор `mp-country` принимает существующие тэги с цифрами, включая D50, после
проверки по настоящему реестру стран. Провинциальную опцию отправляет штатный
callback окна; локальное закрытие подтверждает enqueue, а фактический эффект
нужно проверять отдельно на обоих участниках.

Для полных журналов сетевой приёмки включить `ENABLE_LOG=1` и
`ENABLE_OOS_LOG=1` в обеих тестовых копиях до запуска. `ENABLE_RNG_PROBE` и
`ENABLE_STATE_PROBE` создают дополнительные журналы, но не заменяют SYNC.
`queued=true`, совпадение одного локального снимка и отсутствие файла OOS
с выключенным логированием не подтверждают сетевую согласованность.

Короткий принудительный GPC-прогон допустим только в изолированном тесте:
`VIC2_GPC_TEST_ALWAYS=1` вместе с автоматически назначенным `VIC2_TEST_SESSION`.
После запуска восстановить переменную. Анализатор запускать с
`--require-native-sync --require-gpc-passes 1`; требовать одновременно
`ok=true` и `complete=true`. Сценарий первой Д-корки, религиозного эффекта и
MP-сохранения находится в `tools/culture_religion/mp_acceptance.py`;
результаты — в отчёте приёмки.
