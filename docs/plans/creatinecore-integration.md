# Внедрение CreatineCore, русификация и автоматическая отладка Victoria II

## Результат и принятые решения

Расширить текущую сборку в `D:\v2game`, сохранив её собственные события, решения, карту и локализацию. Включить выбранные возможности CreatineCore и дополнительные исправления существующих скриптовых команд. Добавить управление тестовой игрой из CLI без участия человека.

Зафиксированы следующие решения:

- Основной репозиторий остаётся на текущей ветке `master`. Существующие коммиты сохраняются; каждое законченное осмысленное изменение получает отдельный коммит.
- Репозиторий инструкций подключается как сабмодуль `AGENTS`; его новая ветка `v2game` создаётся от `origin/main`. Исходная рабочая копия `D:\mathloop\AGENTS` остаётся самостоятельной.
- Пользовательские сохранения служат источниками тестовых копий. Их содержимое, имена и расположение не изменяются.
- Для автоматизации допустим скрытый процесс настоящего `v2game.exe`, включая инициализацию графики. Команды выполняются через функции движка, без кликов и ввода в игровую консоль.
- `BUILDING_GOODS_CONSUMPTION` включается как возможность. **Ставки содержания пока откладываются** по последнему согласованному решению.
- `POP_SALARY_ADDITIONAL_MULTIPLIER` включается с явно заданной нулевой глобальной прибавкой.
- Цены используют экспоненциальный алгоритм. Фабричный резерв увеличивается с 1000 до 3000 на уровень; расширение потолка цен выключено.
- Новые игровые тексты, инструкции, сообщения собственных инструментов и отчёты — на русском. Идентификаторы команд и машинные поля сохраняют технические имена.

Основой станет проверенный CreatineCore **6.43**, коммит `7d9f9df9b356096cde475ebd550fbb0102fa1042`. Потребуется собственная сборка: обнаружены расхождение имён настройки содержания зданий и непереведённые строки непосредственно в C++.

## Порядок работы

Применить алгоритм из прочитанного `origin/main:AGENTS.md` и его руководства `task_execution.md`:

1. Первым действием реализации сохранить этот план целиком в отдельном каталоге задачи внутри системного `%TEMP%`.
2. Перед каждой стадией записывать её уточнённый план: изменения, зависимости, проверки, условия завершения.
3. После стадии проводить ревью, исправлять подтверждённые замечания и повторять затронутые проверки до завершения.
4. Сохранять результаты проверок и причины оставшихся ограничений. Заблокированную проверку не считать пройденной.
5. После компактизации сначала перечитывать сохранённый общий план, дополнения и материалы текущей стадии.
6. Параллельно делегировать только независимое исследование или ревью. Изменения Git, сборку и запуск игры выполнять последовательно.
7. Коммитить проверенные изменения; публикация веток на удалённых серверах в этот план не входит.

### Стадия 3. CLI и DLL-мост для отладки

**Архитектура**

```text
Codex CLI → Python CLI → Windows Named Pipe
                         → vic2_test_bridge.dll
                         → функции настоящего движка Victoria II
```

Выбрать собственный небольшой плагин CreatineCore. Использовать исследования Smedley и Victoria2-Reverse-Engineering как источники проверенных адресов и контрактов; второй DLL-загрузчик в игру не устанавливать. Полный Smedley сейчас не предоставляет готового интерфейса выполнения произвольных событий и решений, а совместная установка добавляет пересекающиеся перехваты.

**Интерфейс**

Предоставить единый CLI со следующими операциями:

| Операция | Результат |
|---|---|
| `start --save … --hidden` | Запускает тестовую игру, загружает копию сейва, оставляет кампанию на паузе |
| `status` | Возвращает готовность, дату, страну, версии и действующие патчи |
| `decision check` | Проверяет настоящие `potential` и `allow` указанного решения |
| `decision execute` | Повторно проверяет условия и выполняет решение |
| `event fire` | Вызывает событие с заданной страной/провинцией, контекстом и выбранной опцией |
| `snapshot` | Возвращает запрошенные деньги, флаги, переменные, модификаторы, отношения и данные POP |
| `advance --days N` | Выполняет заданное число игровых дней и снова ставит игру на паузу |
| `save` | Сохраняет результат только в каталоге тестового запуска |
| `stop` | Завершает принадлежащий тесту процесс |
| `run scenario.json` | Выполняет последовательность команд и проверок, выдаёт JSON-отчёт и код завершения |

**Контракты выполнения**

- Использовать локальный именованный канал с идентификатором сессии; команды исполнять последовательно на проверенном потоке движка.
- Обслуживание команд должно работать и на паузе. Поток IPC не обращается напрямую к объектам игры.
- Проверять хеш EXE, сигнатуры, фазу загрузки и совместимость перехватов до вызовов. Неподтверждённый ABI не использовать.
- Для события обеспечить выполнение `immediate` и выбранной опции ровно один раз. Принудительный вызов без проверки trigger обозначать явно в команде и отчёте.
- Не применять автоматическую случайную опцию к событию, опцию которого выбрал тест.
- В обычном выполнении решения соблюдать `potential`/`allow`; отдельный явный `--force` допускается только в тестовой сессии.
- Возвращать понятные ошибки для неизвестных ID, неверного scope, отсутствующей страны/провинции, незагруженной кампании и тайм-аута.
- Не обещать отмену уже начатого эффекта: при аварии или неоднозначном завершении считать сессию непригодной и запускать новую из исходной копии.
- Повторные команды исполнять в загруженной кампании. Для чистого сброса состояния перезапускать процесс; изменение скриптов также требует нового запуска.
- Плагин отладки активировать только для тестового запуска; обычная игра не открывает управляющий канал.

**Статические проверки**

Добавить быстрый CLI-анализ синтаксиса, дублирующихся ID, прямых ссылок и новых локализационных ключей. Переиспользовать подходящий парсер Smedley с усилением диагностики незакрытых строк/блоков. Статический анализ не должен выдавать себя за выполнение условий движком.

**Приёмка**

Из терминала без участия человека проходит сценарий: запуск → загрузка → проверка решения → выполнение → событие с выбранной опцией → проверка состояния → сохранение → выход. Отрицательные проверки дают диагностируемый отказ. Отдельно измеряются время загрузки и задержка команд в готовой сессии.

**Коммиты:** протокол и жизненный цикл; операции движка; CLI, сценарии и диагностика.

### Стадия 4. Выбранные возможности и исправления скриптов

Включить все запрошенные настройки. Для перенаправления урона использовать настоящее имя из кода:

```ini
BUILDING_GOODS_CONSUMPTION=1
ENABLE_IF_ELSE_OPERATORS=1
FIX_PROVINCE_FLAGS=1
NEW_POP_MODIFIERS=1
CREATE_SUBSTATE=1

ENABLE_VASSAL_COLORS=1
VASSAL_COLOR_PERCENT=65
NAVY_ALLOW_USE_ALLY_TRANSPORTS=1
COMBAT_SECOND_LINE_SUPPORT_UNIT_PRIORITY=1
COMBAT_SECOND_LINE_DAMAGE_REDIRECT=1
ARMY_FIX_BAD_REINFORCEMENT=1
NAVY_FIX_BAD_REINFORCEMENT=1
ARMY_BETTER_REINFORCE_ON_ALLIED_OWNED_LAND=1

```

`BATTLE_SECOND_LINE_DAMAGE_REDIRECT` из README — устаревшее имя; в выбранном исходнике действует `COMBAT_SECOND_LINE_DAMAGE_REDIRECT`.

Дополнительно включить:

- `FIX_MEMORY_MISS_CRASHES`: сохранение корректного `FROM` в отложенных событиях.
- `FIX_TECH_FACTORY_MAINTENANCE`: действие модификатора в технологиях и изобретениях.
- `POP_FIX_NEEDS_MODIFIERS` и связанные исправления отображения потребностей и бюджетных выплат.
- `ACTIVATE_DEACTIVATE_UNIT`: корректная поддержка активации/деактивации частей.
- `NEW_COUNTRY_SCOPE_CONDITIONS`: условия религии страны и доступности типа войск для соответствующих сценариев.
- `FACTORY_AI_FACTORY_PRIORITY_RULESWAP`: правильное применение существующего правила `factory_priority`.
- Защиты от отсутствующих объектов при цивилизации, открытии технологий и определении источника снабжения.

Из дополнительного оптимизатора перенести в отдельный узкий плагин исправления отсутствующих модификаторов, условия `date` и своевременной проверки событий с календарными ограничениями. Не подключать вместе с ними изменение частоты сканирования, правила марионеток, удаление армий и пропуск стран. Ошибочные ссылки на модификаторы должны диагностироваться.

Для начального профиля оставить сжатие кэша флагов и предварительную загрузку данных POP/отношений. Параллельные события/решения, изменение AI-очереди, квантование POP и комплект дополнительных оптимизаторов выключить. Все остальные переключатели задать явно, чтобы обновлённые defaults не добавляли незапрошенное поведение.

**Приёмка**

Лог подтверждает установку каждого выбранного hook. Контрольные сценарии проверяют ветвления, флаги, scope, отложенный `FROM`, новые POP-модификаторы, обе формы `move_pop`/`assimilate`, подчинение и вступление в войны. Повторная загрузка сохраняет соответствующее состояние.

**Коммиты:** профиль расширений; дополнительные исправления существующих команд.


### Стадия 5. Экономика и подготовка содержания зданий

**Цены и фабрики**

```ini
TRADE_PRICE_DELTA_PERCENTUAL=0
TRADE_PRICE_DELTA_EXPONENTIAL=1
TRADE_MAX_PRICE_20X_MULTIPLIER=0
```

- Изменить `MAX_FACTORY_MONEY_SAVE` с 1000 на **3000**. Это резерв на уровень фабрики; увеличение также откладывает выплаты владельцам.
- Обосновать значение примером GFM. Не представлять его как указанное разработчиком число или универсальное устранение переполнений.
- Проверить движение цен, денежные резервы, выплаты владельцам и отсутствие некорректных отрицательных/переполненных величин на позднем сохранении.

**Расширения экономики**

- Задать глобальную прибавку доходов POP равной нулю; в тестовом сценарии проверить ненулевой `pop_income_modifier`.
- Проверить использование старого `rgo_input` в игровых данных и выбранных сейвах: CreatineCore переименовывает этот слот. При обнаружении реального использования сохранить совместимость через alias/миграцию с регрессионным тестом.
- В основной кампании не добавлять `goods_consumption` зданиям.
- В тестовом моде добавить пример реальной закупки и проверить стоимость, дефицит товара, нехватку казны и отсутствие двойного списания после загрузки.
- Добавить место для расходов на содержание в окне бюджета и русские подсказки.

**Исследование ставок**

Сохранить результаты проверки закреплённых версий BDSM, GFM и TGC. Подтверждён один независимый профиль ненулевого содержания — морские базы BDSM. Медиану нескольких модов не вычислять, документационный пример железных дорог не считать наблюдением. Ввод ставок остаётся отдельной будущей задачей.

**Приёмка**

Экспоненциальный алгоритм действительно активен; резерв соответствует настройке и уровню фабрики. Глобальной прибавки доходов POP и новых расходов зданий в обычной кампании нет; обе возможности работают в изолированных тестах.

**Коммит:** ценообразование, фабричный резерв и проверенная поддержка экономических расширений.

### Стадия 6. Полная русификация и визуальная проверка

**Действия**

- Перевести все новые эффекты, условия, модификаторы, сообщения и подсказки выбранных возможностей.
- Добавить отсутствующие строки расходов зданий, фабричного обслуживания и доходов POP, включая оба ключа `MODIFIER_RGO_INPUT` и `RGO_INPUT_TECH`.
- Заменить жёстко записанные в C++ английские подписи флагов провинций и диагностики модификаторов локализационными ключами.

Если подключение недоступно, использовать ограниченный локальный хелпер для снимков окна и проверки нужных экранов. Это вспомогательная проверка интерфейса, независимая от CLI-моста.

**Коммит:** русские тексты и необходимые изменения интерфейса.

### Стадия 7. Проверка сохранений и завершение установки

Использовать копии:

- `1841.v2` — ранняя кампания;
- `1891.v2` — середина игры;
- `1931.v2` — развитая поздняя экономика;
- `isolation_baseline.v2` — небольшой исходный сценарий для быстрых тестов.

**Основные проверки**

1. Для трёх обычных сейвов: загрузка → 30 игровых дней → сохранение под новым именем → перезапуск → загрузка результата → ещё один день.
2. Для позднего сейва дополнительно пройти 90 дней с экспоненциальными ценами, проверяя денежные величины и состояние фабрик.
3. Проверить запуск новой кампании 1836 года.
4. Выполнить компактный набор регрессий выбранных расширений через CLI.
5. Отдельно проверить сохранение и загрузку армии на союзном транспорте, пополнение при неполном снабжении, приоритет второй линии и перенаправление урона с задней целью и без неё.
6. Проверить музыкальные triggers и выбор из набора более десяти допустимых композиций.
7. Повторно сверить хеши исходных пользовательских сейвов.

Сравнение с исходной сборкой используется для выявления сбоев и грубых отклонений. Побитовое совпадение симуляции не требуется: выбранные исправления и экономика намеренно меняют результаты.

После успешных проверок перенести проверенный комплект в основную сборку, выполнить заключительный запуск и записать инструкцию по запуску игры, CLI-тестам, обновлению и откату. В отчёте указать версии, коммиты, фактические результаты и оставшиеся ограничения.
