# Нативное управление сетевыми меню без мыши и клавиатуры

Статическое исследование `v2game.exe` 3.04, SHA-256
`62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`.
Все адреса — VA при image base `0x400000`. Выполнение игры этим исследованием
не проверялось. Документ описывает вызовы контроллеров, пригодные для расширения
CLI; существование оконного объекта движка не требует физических кликов.

## Найденные пути к контролам

Существующий `tools/vic2test/native/bridge.cpp` уже квалифицировал:

```text
mainMenu: ctor 00754A00, vtable 00E13DBC, destructor 00754DF0
frontend: ctor 0076A2F0, vtable 00E14ED0, destructor 0076B030

FindControl(object, slot, name):
  ECX=object, push &GameString(name), call object.vtable[slot/4]

Signal(button):
  EAX=button+54, call 009EE510 (press)
  EAX=button+54, call 009EE550 (release)
```

Здесь `slot` — смещение в **байтах**, а не номер элемента массива.
`Signal` запускает настоящих подписчиков кнопки, без WM_MOUSE/SendInput.

Вход в сетевое меню использует тот же квалифицированный путь:

```text
panel = FindControl(*(mainMenu+704), 6C, "mainmenu_panel")
button = FindControl(panel, 34, "multi_player_button")
Signal(button)
```

`CMultiplayerMenuView` строится `00763520`, получает vtable `00E14844`.
Поля его объекта:

| Смещение | Значение | Статическое доказательство |
|---|---|---|
| `+4` | родительский controller/idler | `0076353B..00763544` |
| `+368` | окно `multiplayer_menu` | `0076374F..00763755` |
| `+36C` | созданное окно `naming_window` | `00763B14..00763B5E` |
| `+370` | окно `multiplayer_connect_menu` | `00763752..0076375B` |

Вызов конструктора `0075A3EC` записывает результат в элемент 4 вектора экранов.
Функция `007599E0` работает с **вторичным this = root+0x88**: конструктор
`00754A30..00754A49` создаёт в `root+0x88` подобъект с vtable `0xE13F5C`.
Дополнительный якорь: её `[EBX+0x67C]` соответствует квалифицированному GUI-root
`[root+0x704]`. Поэтому начало/конец вектора на первичном объекте `CFrontEnd` —
**`root+0x74C` и `root+0x750`**, а не `+0x6C4/+0x6C8`.

Вектор содержит **непосредственно view-указатели**. Запись `[[EBX+6C4]+10]=eax`
означает индекс 4 массива, а не поле `holder+0x10`. Искать MP-view следует
ограниченным обходом всего этого массива с проверкой vtable `base+0xA14844`
и `[view+4]==root`; порядок элементов не является интерфейсным контрактом.

Главный агент подтвердил это чтением живой памяти: у `root=0x254CF230`
`+0x74C=0x4EEA5580`, `+0x750=0x4EEA55A0` (8 указателей), элемент 3 — SP-view
`0x26EA38D8` с vtable `base+0xA14ED0`, элемент 4 — MP-view `0x49E6D350` с vtable
`base+0xA14844`; оба `view+4` равны root. Это runtime-подтверждение передано
главным агентом; данным исследователем игра не запускалась.

После Signal multi_player_button функция Open возвращает состояние, даже если
view ещё не готов. Продолжение должно опрашивать Inspect без повторного Signal.
Ошибка E_NOT_READY после уже выполненного перехода не используется как команда
автоматически повторить переход.

Контролы сетевого меню (`interface/temp_frontend.gui`):

- `FindControl(*(mp+368), 34, "host")`;
- `FindControl(*(mp+368), 34, "join")`;
- `FindControl(*(mp+368), 34, "join_direct")`;
- `FindControl(*(mp+368), 40, "playername")` — **editBox**, другой слот поиска;
- `FindControl(*(mp+36C), 40, "edit")` — поле имени сервера либо адреса;
- `FindControl(*(mp+36C), 34, "ok_host_button")` — подтверждение активного режима;
- `FindControl(*(mp+36C), 34, "back_button")` — отмена.

Типы и имена подтверждены файлом интерфейса и кодом: кнопка join_direct ищется
через `vt+34` в `00763ADB..00763AEA`; playername/edit — через `vt+40` в
`0076409D..007640AC` и `007641F2..00764201`.

Не подменять подтверждение окна прямым вызовом одного callback: набор
подписчиков `ok_host_button` меняется при переключении host/join. Настоящий
`Signal` выбирает подписчика, установленного текущим контроллером.

## Строка editBox: SetText и GetText

У найденного объекта editBox текстовый компонент расположен **inline в `box+54`**.
Vtable читается с `*(box+54)`, а не с `*box`.

### SetText

```cpp
using SetText = void (__thiscall*)(void* textComponent, const GameString* text);
SetText setter = reinterpret_cast<SetText>(Read(Read(box+0x54)+0x40));
setter(reinterpret_cast<void*>(box+0x54), &text);
```

Два независимых реальных вызова:

- `007640AE..007640C7`: после поиска playername, `ECX=box+54`, передаёт указатель
  на сохранённое имя игрока из объекта настроек/локализации `+108`, вызывает
  виртуальную функцию `vt+40`.
- `00765015..0076501D`: текстовое содержимое naming_window.edit заполняется тем же
  слотом `vt+40` после форматирования `FE_MY_GAME`.

В обоих случаях ровно один указатель на строку в стеке, ECX — компонент,
ручного caller cleanup нет. Это контракт thiscall с callee cleanup четырёх байт.
Конкретный адрес реализации получается из проверенного runtime-vtable; один
фиксированный адрес SetText пока статически не квалифицирован.

### GetText

```cpp
using GetText = GameString* (__thiscall*)(void* textComponent, GameString* result);
GetText getter = reinterpret_cast<GetText>(Read(Read(box+0x54)+0x4C));
getter(reinterpret_cast<void*>(box+0x54), &result);
```

- `007652C3..007652CF`: читает имя игрока, ECX=box+54, передаёт адрес локального
  объекта строки и получает указатель на неё в EAX.
- `00767D18..00767D28`: настоящий host-confirm читает naming_window.edit тем же
  слотом, затем копирует строку в настройки создаваемой сессии.
- `00767E28..00767E38`: читает playername тем же контрактом.

Это возврат строки через caller-provided буфер. Если результат использует heap,
его необходимо освободить **игровым** деструктором строки `00408AD0`, ECX=&result.
Передавать `std::string` современного MSVC нельзя. Для входа достаточно старого
24-байтного ABI (`inline[16]/pointer`, length `+10`, capacity `+14`); короткое
ASCII-имя/адрес упрощает первый квалификационный эксперимент. После SetText
обязательно проверить GetText и только затем Signal подтверждения.

Слоты SetText/GetText нельзя применять к произвольной кнопке: сначала проверять
успешный lookup editBox, читаемость компонента и принадлежность функций к EXE.
Это отдельный qualification gate перед автоматическим host/join.

## Lobby и сохранение

У `CFrontEnd` корневое окно lobby находится в `[frontend+278]`, что совпадает
с квалифицированной SP-командой play. Сам объект общий для нового сценария и
сохранения; сетевой режим требует отдельного runtime-подтверждения.

Имена и типы элементов из `interface/lobby.gui`:

| Элемент | Поиск |
|---|---|
| `play_button` | корень lobby, `slot 34` |
| `playable_countries_window` | корень lobby, `slot 6C` |
| `playable_countries_list` | окно стран, `slot 7C` |
| `save_games` | корень lobby, `slot 6C` |
| `save_games_list` | окно сохранений, `slot 7C` |
| `save_game` | окно строки сохранения, **checkbox, slot 48** |
| `playable_countries_button` | окно строки страны, `slot 34` |

Слоты поиска listbox и checkbox подтверждаются `0076D3FB..0076D407` и
`00777F75..00777F86`. Последовательность строителя списка стран добавляет row
через `listbox.vt+10(row, 0)` (`0076D58E..0076D597`); внутреннее устройство
списка row-объектов этим ещё не установлено. Для его обхода нельзя угадывать
смещения по другой разновидности GUI-списка.

SP `load-save`, как и квалифицированный сетевой выбор сохранения, вызывает
штатный обработчик `00777DB0` (this=frontend, один stackarg clicked checkbox,
ret4) для настоящей строки `CSavegameItem` из `bookmarks_list`. Мост проверяет
vtable строки `00E15190`, basename в row+28, checkbox `save_game` и
однозначность выбора. Callback ставит служебное действие `CClearBookmark`
в очередь, меняет выбор строки, в `00777FB0..00777FBF` копирует **basename**
в `frontend+590`, затем вызывает `00778080` (`00778058..0077805A`). Прежняя
прямая запись имени в `590` и флага `5BC=1` обходила часть обработчика и
больше не используется. Она не является эквивалентом полной операции.

Для SP готовность `frontend-status.save_loaded` требует `5BD=1`, `5BC=0`
и доступную `play_button`: нативный getter `vt+B0`, состояние 3 означает
недоступность. `play` проверяет тот же критерий перед обычным Signal. Эти
проверки готовности frontend не обещают заполнения реестра случайных событий
сразу после загрузки сохранения; это отдельный контракт ниже.

Настоящая кнопка play подписана на observer `frontend+1D8`
(`0076ABCD..0076ABDD`), чей callback установлен в конструкторе как **00772300**
(`0076A51F..0076A52D`). Следовательно, существующий Signal play_button идёт по
правильному пути, но разрешение старта/готовности всех клиентов надо подтвердить
по результату сессии. Callback `007733A0` не является play: он выбирает страну
по другому набору кнопок/щитов.

## Холодная загрузка и месячный реестр событий

Штатный `CInGameIdler::Initialize` находится по `00662010`: vtable
`00E0A34C`, слот `+0C`. Вызов `009DF9D2..009DF9DD` передаёт this через ECX,
без stackargs; завершение `006692E9` — обычный ret. Внутри Initialize чтение
`world+D10` в `00663209` и переход `00663217 → 0066364E` при ненулевом флаге
обходят стартовый daily/monthly блок, включая вызов месячной обработки в
`006633A8`. Поэтому пустой начальный event cache загруженного сохранения сам
по себе не означает незавершённый Initialize или дефект CLI load.

При обычном ходе времени месячная фаза вызывается в `00683B36 → 00687E30`,
затем `00687F83 → 008A78D0 → 008A7700`. Она использует тот же менеджер из
глобального указателя `01319B80`, что и ежедневный провинциальный скан
`008A7CD0`. В менеджере `+20/+24` ограничивают общий вектор провинциальных
событий, `+30/+34` — реестр случайных; месячная обработка строит последний
и списки кандидатов провинций `+14/+18`. Флаг tutorial `world+D11` — отдельное
условие естественного скана, его нельзя смешивать с веткой загрузки `D10`.

Опыт `natural-native-month-10` на настоящем движке подтвердил этот путь:
после холодной CLI load `random_province_events=0`, на raw date `59884104`
(+31 день от 1836.1.1) — `1824`. Нативная диагностика подтвердила присутствие
OBO24754 в списке провинции 546. На +32 окно события появилось после возврата
`advance`; прежний runner ошибочно вызвал `settle` и завершился отказом из-за
открытого окна. Этот опыт подтверждает месячное обновление и появление окна,
но сам по себе не подтверждает завершённый автоматический выбор и итоговую
корку. Свежая GUI-кампания имеет отдельное
[подтверждение полного естественного срабатывания](chronology-core-events.md#подтверждённое-естественное-срабатывание).

Ранее опыт `natural-native-callback-09` сохранил начальные random/cache=0
после перехода на полный save-row callback. Следовательно, callback нужен
для правильного frontend-пути, но предположение, что он устранит начальный
пустой реестр, опровергнуто. Дополнительную обёртку Initialize не подключали:
имеющиеся наблюдения не доказывают необходимость нового hook. Ручной вызов
init или построение списков не используются.

`status.all_province_events` и `status.random_province_events` читают только
проверенные границы векторов; в меню и при неизвестном layout возвращают
`null`. Перед измеряемым интервалом после каждой загрузки выполнить одинаковый
прогрев через смену месяца для сравниваемых наборов, затем потребовать
`random_province_events > 0`. Не включать прогрев в измеряемое время и не
считать число общего реестра доказательством участия конкретного события:
это показывает `event-check.cached.contains`. Raw date сдвигается до конца
обработки дня; `event-check` отказывает при `world+B20` (day busy). Проверка
автоматической опции должна учитывать окно, появившееся после барьера даты.

## Выбор страны проходит через сетевую очередь

Объект строки страны строится `00769020`, размер `0x88`, vtable `0xE150CC`.

| Поле row | Значение |
|---|---|
| `+20` | окно строки GUI |
| `+28` | packed TAG |
| `+2C` | индекс страны |
| `+30` | frontend controller |
| `+38` | observer кнопки |

Конструктор сохраняет параметры в `007690DE..007690F4`, подписывает кнопку
`playable_countries_button` (`007691ED..00769208`). Observer dispatch `0077A0A0`
идёт в `row.vtable+10`, где указатель **00769580**.

`00769580` — thiscall, this=row, без stackargs, обычный ret. Выполняет:

1. Выделяет страну/её столицу для представления карты.
2. Получает сессию через виртуальный метод `frontend+3C`, слот `+28`.
3. Создаёт действие размером `0x50` функцией **007297A0**.
4. Передаёт действие очереди `[session+38].vt+18`.

Конструктор действия `007297A0` имеет **шесть stackargs**, `ret 18h`, результат
в EAX. По caller `0076960A..00769627` порядок аргументов:

```text
(allocated_object, packed_tag, country_index,
 world_B5C, world_B60, session_6C)
```

Действие получает vtable `0xE11F3C` (`0072982B`); поля `+3C/+40` хранят TAG/index,
`+44/+48/+4C` — остальные три значения. Полное семантическое имя каждого из
этих трёх полей без дальнейшего исследования не назначается.

**Предпочтительный путь CLI:** найти настоящий row по квалифицированным
TAG/index и выполнить Signal её кнопки. Прямое создание действия возможно
после проверки его ABI и владения в очереди; локальная перезапись выбранной
страны не воспроизводит сетевой протокол.

## Критерии runtime-квалификации без физического GUI-ввода

1. Захватить существующий MP-controller и проверить vtable/деструктор.
2. Через FindControl установить и прочитать обратно playername; открыть host
   либо join_direct, установить/прочитать edit, подтвердить Signal.
3. Убедиться, что создаётся настоящая host/client-сессия и появляется общий lobby.
4. Выбрать сохранение хостом штатным путём, дождаться его передачи клиенту;
   наличие одинакового файла на диске не заменяет передачу внутри сессии.
5. Выбрать разные страны и дождаться применения queued selection на обеих
   сторонах. queued=true не означает completed=true.
6. Signal play_button хоста должен привести к настоящей общей кампании,
   а не двум независимым SP-мирам.

Все вызовы контроллеров выполнять на уже квалифицированном потоке владельца
из существующего CLI-моста. Сворачивание/скрытие окон не меняет требование к
настоящему циклу сообщений, рендеру и инициализированной сессии движка.
