# GPC: статические контракты планировщика, MTTH и глобальных флагов

Дата исследования: 2026-11-15. Исследован установленный `v2game.exe` с SHA-256
`62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`.
Исходная база образа — `0x00400000`; ниже VA обозначает адрес относительно этой
базы, RVA = VA − `0x00400000`. При ASLR использовать фактическую базу модуля.

Это **статическое исследование**, а не разрешение считать адаптеры проверенными
на работающей игре. Игра в рамках исследования не запускалась; SP/MP, сохранение
и восстановление новых флагов ещё требуют квалификации.

Источники: дизассемблирование `.work/creatinecore/game-disassembly.txt`, байты
указанного EXE и закреплённый CreatineCore
`7d9f9df9b356096cde475ebd550fbb0102fa1042`:
`V2TechButton.cpp` (ParallelEvents, Event-roll probe, RNG probe, DecisionCull),
`CCore_ProvinceFlags.cpp` и `v2dll_country_daily_optimizer/v2dll_mod.cpp`.
Комментарии upstream использовались как ориентир; основные выводы ниже сверены
с инструкциями EXE.

## 1. Общая фаза и частота проверки событий

В дневной обработке `FUN_006859C0` найден единственный прямой вызов
`FUN_008A7CD0`, сканирующий естественные события:

```text
006861E7  push esi                ; CEventManager*
006861E8  call 008A7CD0
006861ED  mov ecx,[ebx+0AE0h]      ; продолжение дневной обработки
```

По адресу вызова находятся байты `E8 E3 1A 22 00`. RVA участка — `0x2861E8`,
цели — `0x4A7CD0`. Пролог цели: `55 8B EC 83 E4 F8`; завершение по
`0x008A811C` — `ret 4`. Аргумент менеджера читается как `[ebp+8]` и передаётся
в исполнение события. Статически достаточная сигнатура сканирования:

```cpp
void __stdcall EventManagerDailyScan(void* event_manager);
```

Возвращаемое значение вызывающей стороной не используется. Кандидат точки GPC —
сразу после возврата этого вызова, до продолжения дневной обработки. Это общая
фаза обработки событий, но **не конец всего игрового дня**. Не подменять её
обработчиком отдельной страны `CountryDailyHook`: последний вызывается перед
штатным обновлением каждой страны.

`FUN_006859C0` имеет как минимум три прямых вызывающих участка:
`0x00663234`, `0x0066339D`, `0x00683AB1`. По одной только общей функции нельзя
объявить доказанной одинаковую частоту SP и MP. В квалификационном прогоне надо
зафиксировать идентификатор потока, дату, число вызовов и положение относительно
штатного сканирования на обоих участниках.

Участок `0x2861E8` также использует upstream `ParallelEvents::ScanThunk`.
Текущий профиль отключает `PATCH_PARALLEL_EVENTS`; оптимизатор сканирования
событий также не установлен как общий optimizer. Новый модуль не должен
молча перезаписывать чужой прыжок. Проверять исходную цель и конфликт установщиков;
если впоследствии понадобится совместная работа, использовать один общий
владеющий этим call-site диспетчер.

### Чередование стран и провинций

В начале `FUN_008A7CD0` из `world = *(base + 0xE588E8)` читается
`world+0xB0C`. Это дата в часах. Инструкции `0x008A7D10…0x008A7D42` вычисляют:

```text
day = trunc_toward_zero((date_raw - 0x029C55C0) / 24)
country_pass = (day % 2 == 1)
```

На нечётной ветви обрабатываются страны, на другой — провинции. Для игровых
дат кампании разность положительна. Следовательно, обычное страновое событие
получает попытку **через день**, если находится в списке кандидатов и проходит
свой trigger. Ежедневный GPC-обработчик может быть дешёвым, но расходовать свой
RNG и выполнять попытку с нативным порогом должен на страновой фазе, иначе
частота будет удвоена.

Списки кандидатов обычных событий перестраиваются отдельно; GPC не нужен такой
список, поскольку его глобальная попытка всегда доступна. Перестройку списков
не следует ошибочно считать ещё одним множителем MTTH.

## 2. Парсер MTTH и целочисленный порог

Регистрация ключей в EXE:

| Ключ | Token | Участок регистрации |
|---|---:|---:|
| `months` | `0x3BF` | `0x00C4232C` |
| `days` | `0x3C0` | `0x00C42358` |
| `years` | `0x3C1` | `0x00C42384` |

Парсер MTTH `FUN_008AE8A0`, `ECX = mtth_object`, стек `(parser, token)`,
`ret 8`, сохраняет базовое значение по `mtth_object+8`.
`FUN_0098FB60` разбирает число в fixed-point с масштабом 1000.
Ветка `months` по `0x008AE941` умножает это число на `0x7530 = 30000`
и делит на `1000`. Ветка `years` использует `0x591C8 = 365000`.
Ветка `days` записывает разобранное значение непосредственно.

Таким образом, без модификаторов:

```text
months = 60
parsed_fixed = 60000
mtth_object[+8] = 60000 * 30000 / 1000 = 1800000
```

В страновой ветви сканирования наблюдается:

```text
008A7DF7  push 1
008A7DF9  lea eax,[esp+44h]       ; scope
008A7DFD  push eax
008A7DFE  lea ecx,[ebx+0C0h]      ; event + 0xC0 = MTTH
008A7E04  push ecx
008A7E05  call 008AE380
```

`FUN_008AE380` получает все три аргумента из стека, возвращает порог в `EAX`
и заканчивается `ret 0x0C`. Это не thiscall:

```cpp
int32_t __stdcall EvaluateMtthChance(
    void* mtth_object, void* event_scope, int32_t multiplier);
```

У объекта читается базовое значение `+8` и вектор модификаторов `+0x0C…+0x10`.
Если модификаторов нет, положительное значение больше 1000 преобразуется в:

```text
whole_days = trunc(mtth_fixed / 1000)
threshold = clamp(trunc(multiplier * 1000000 / whole_days), 1, 1000000)
```

Ветка `mtth_fixed <= 1000` возвращает `1000000`; отрицательные значения имеют
дополнительную проверку исходного базового значения. Для новых настроек
рекомендуется отвергать неположительные значения, не наследовать эти ветви
ошибочных конфигураций.

Для `months=60`, `multiplier=1`, пустого списка модификаторов результат — **555**.
В `0x008A7EB1` сравнивается `rnd < threshold`; `rnd` получен штатным RNG и
приведён к диапазону остатком от деления на `1000000`.

Это означает семантику порога 555 на страновой фазе через день. Нельзя заменять
её ежедневной вероятностью `1/1800`, экспоненциальным «периодом полураспада» или
утверждением, что фактическое среднее ожидание равно ровно 60 календарным
месяцам. Новый собственный RNG с unbiased-преобразованием сохранит выбранную
дискретизацию и порог; побитовую последовательность и небольшой modulo bias
штатного генератора он воспроизводить не будет.

Квалификация: загрузить обычное событие с `months=60` и без модификаторов,
прочитать его `event+0xC8`, вызвать/наблюдать evaluator и сравнения. Ожидания:
`1800000`, `555`, попытки только на страновых фазах. Повторить с `months=1`
(`30000`, порог `33333`) и `days=1` (`1000`, порог `1000000`). Ускоренные
профили не заменяют проверку значения 60.

## 3. Кандидат синхронного начального seed

`FUN_009B7D30`, RVA `0x5B7D30`, не имеет аргументов; возвращает `EAX` через
хвостовой вызов `FUN_009B7610`. Статический кандидат интерфейса:

```cpp
uint32_t __cdecl GameRandomInteger();
```

Он увеличивает общий счётчик по VA `0x00F20C14`, использует singleton по
`0x00F20C18` и состояние генератора по `0x00F0ECF0`. Если singleton отсутствует,
пытается выделить его через игровой allocator. Пролог:
`83 3D <base+0xB20C18> 00`; абсолютный операнд релокируется, поэтому сравнивать
его с жёстко записанным адресом нельзя.

Код ядра `0x009B7610` использует нестандартный вход `EAX = rng_state`, а не
обычный C++ ABI. Для seed предпочтительнее wrapper `0x009B7D30`, учитывающий
штатный счётчик; прямой вызов ядра скрывал бы дополнительное потребление RNG
от этой части сетевой диагностики.

Вызывать только при первой инициализации состояния, в одной и той же
подтверждённой фазе SP/MP. После загрузки существующего GPC-состояния или при
выключенной функции вызова быть не должно. Не вызывать из GUI, IPC, загрузчика
DLL либо чтения диагностики. Ненулевой seed для собственного генератора
получается с документированной заменой нуля; нельзя предполагать, что данный
wrapper выдаёт все 32 бита равномерно.

## 4. Контейнер глобальных флагов и нативные операции

Контейнер находится по `world+0x64`. Это подтверждают:

- конструктор мира `0x0067F811`, записывающий vtable `0x00DF817C`;
- getter `0x0068BEF0`: `add eax,0x64; ret`;
- штатные эффекты установки/очистки и trigger проверки.

Второй подобъект сериализации находится по `world+0x88`, vtable
`0x00DF81A0`. Его методы сдвигают `this` на `-0x24` к основному контейнеру.

| Операция | VA / RVA | Статический ABI |
|---|---|---|
| `set_global_flag` Execute | `0x00882B60` / `0x482B60` | ECX=effect; два аргумента в стеке, `ret 8` |
| `clr_global_flag` Execute | `0x00882BA0` / `0x482BA0` | ECX=effect; два аргумента в стеке, `ret 8` |
| `has_global_flag` Evaluate | `0x008CD1B0` / `0x4CD1B0` | ECX=trigger; scope в стеке, `ret 4`; результат AL |
| Общий set helper | `0x0043C450` / `0x03C450` | EAX=`const char* name`, ESI=container; `ret` |
| Общий clear helper | `0x0043C470` / `0x03C470` | ECX=container, EDX=`const char* name`; `ret` |
| Создание записи | `0x0043C3F0` / `0x03C3F0` | EDI=name, container в стеке; `ret 4`; EAX=entry |
| Lookup, vtable+8 | `0x009E6B10` / `0x5E6B10` | ECX=container, name в стеке; `ret 4`; EAX=entry/null |

У effect имя — игровая строка по `+0x20`, capacity по `+0x34`; у trigger —
строка по `+0x1C`, capacity по `+0x30`. Порог SSO — 16. Нельзя передавать
современный `std::string` вместо этого ABI.

Vtable штатного set-effect: `0x00E2AD68`, clear-effect: `0x00E2ADA0`; Execute
в slot 11. Vtable глобального trigger: `0x00E30820`, Evaluate в slot 6.
Tokens ключей `set_global_flag`, `clr_global_flag`, `has_global_flag`:
`0x79B`, `0x79C`, `0x79D` соответственно.

Lookup возвращает запись с игровой строкой по `+0` и признаком активности
`uint8_t` по `+0x1C`. Set найденной записи ставит этот байт в 1; при отсутствии
создаёт запись через игровой allocator и штатное добавление контейнера.
Clear **не удаляет узел**, а ставит признак в 0. Для адаптера следует вызывать
штатные helpers; нельзя заменять создание записи самостоятельным изменением
дерева или аллокацией через CRT модуля.

Сохранение контейнера: `0x0043C4F0` передаёт корень в `0x0043C490`.
Обход по `0x0043C4B8` проверяет `entry+0x1C`; записываются только активные
записи. Загрузка `0x0043C510` создаёт запись и устанавливает её bool по token
`0x29F` (`yes`). Статически это объясняет хранение внутри обычного `.v2`, но
проверка записи реальных GPC-флагов и повторной загрузки остаётся обязательной.

## 5. Ограниченный кодек состояния

Не применять имена с текущим численным значением или номером прохода,
например `cc_gpc_rng_12345678`: очищенные записи остаются в памяти, поэтому
словарь таких имён будет расти даже при небольшом размере очередного сейва.

Варианты фиксированного словаря:

| Кодирование | Размер словаря для одного uint32 | Свойства |
|---|---:|---|
| Один флаг на бит | 32 | Отсутствие означает 0; потерю флага нельзя отличить от корректного нуля |
| Два флага на бит (`_0`/`_1`) | 64 | Ровно один активен; оба/ни одного означают повреждение |
| Один из 16 флагов на полубайт | 128 | В сейве активны 8; в памяти со временем могут появиться все 128 |

Для требования явно обнаруживать повреждённое состояние рекомендуется пара
флагов на каждый бит версии, начального seed, текущего RNG, последней даты и
номера прохода. Для пяти uint32 это 320 возможных имён и 160 активных флагов,
плюс фиксированные служебные маркеры. Например, `cc_gpc_rng_b00_0` и
`cc_gpc_rng_b00_1`. Версия также должна быть декодируемым числом, чтобы отличать
новую неподдерживаемую версию от отсутствующего состояния.

Инициализацию старого сейва разрешать только при полном отсутствии собственных
известных маркеров/полей. Частично существующее состояние не превращать в новый
seed. Во время пакетной записи использовать фиксированный маркер незавершённого
обновления; наличие такого маркера при чтении — диагностируемый отказ,
а не разрешение повторить выдачу. Записывать изменившиеся значения в одном
синхронном callback, без промежуточного сохранения или пользовательского ввода.

Пара флагов обнаруживает пропущенный/двойной бит, но не произвольную замену
одной корректной пары другой; при необходимости полной проверки целостности
добавляется отдельная фиксированная контрольная сумма. Это решение нельзя
подменять обещанием, что формат распознаёт любое ручное изменение сейва.

## 6. Что ещё обязательно подтвердить

1. Фаза после `0x008A7CD0` исполняется ровно один раз на дату на одинаковом
   потоке симуляции у хоста и клиента. Смена скорости, пауза, перехост и загрузка
   другой кампании не создают повторного расходования собственного RNG.
2. Нативный MTTH-объект действительно содержит 1800000 и возвращает 555 для
   `months=60`; журнал попыток подтверждает найденную нечётную фазу.
3. Wrapper seed вызывается один раз при инициализации и ни разу при чтении,
   повторной загрузке готового состояния или выключенной функции.
4. Set/clear/has совпадают с настоящими скриптовыми условиями; новое имя,
   повторная установка, очистка отсутствующего имени и повторная установка
   очищенного имени работают без роста числа узлов за пределы словаря.
5. Сохранение содержит активные поля, новый процесс и другая кампания в том же
   процессе корректно восстанавливают/изолируют состояние; старый сейв
   инициализируется, повреждённый и неизвестной версии отвергаются явно.
6. Флаги и счётчики совпадают у обоих сетевых участников после каждого
   контрольного прохода. Статическая общность функции и отсутствие окна OOS
   этого не доказывают.

До этих проверок контракты имеют статус «кандидат, подтверждённый статически»;
зависимую производственную функцию нельзя считать готовой или включать в
основную сборку.
