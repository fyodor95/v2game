# Вестернизация: очки исследования и выдача технологий

Исследовано 18.11.2026 для рабочей сборки на коммите `d44bd52e`.
Основание — дизассемблирование конкретного `v2game.exe` Heart of Darkness 3.04,
SHA256 `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`.
ImageBase `00400000`; все адреса ниже — VA, RVA получается вычитанием `00400000`.
Это реконструкция машинного кода, а не доступ к исходникам Paradox.
Игры для этого исследования не запускались, игровые данные не изменялись.

## 1. Очки исследования

**Сама вестернизация сохраняет весь накопленный запас**, включая превышение
нового цивилизованного лимита. Выдача технологий не оплачивается этим запасом.
Однако сохранность превышения после следующего дня зависит от активного
исследования.

Страновое поле `+E3C` содержит запас RP в тысячных долях очка. Это доказывается
загрузчиком `research_points` (`004FBCB1–004FBCBA`) и консольным обработчиком
`researchpoints` (`0041C17B–0041C190`), который умножает аргумент на 1000,
прибавляет запас и вызывает setter `005366F0`.

В функции вестернизации `00542370–00542BB7` нет присваивания этому полю,
вызова setter либо дневного обновления исследований. По `00542875` меняется
флаг цивилизованности `country+12D0`, затем пересчитываются технологии,
постройки и производные параметры (`00568C80`, `00508330`, `0050EA30`).
Эти вызовы не переводят запас RP через setter. Далее вызывается `on_civilize`.
Текущие события 90900/90903/90910 не списывают RP и не выдают технологии:
они меняют престиж, модификаторы и отношения китайских образований.
Удаление модификаторов может изменить последующую дневную генерацию и лимит.

Лимит рассчитывается так:

```text
нецивилизованная страна: MAX_RESEARCH_POINTS = 25000 RP
цивилизованная страна: 365 × текущая дневная генерация RP
```

Доказательство: setter `005366F0–00536763`, особенно `00536739–00536759`.
Для нецивилизованных берётся `defines.country+158`; его связь со строкой
`MAX_RESEARCH_POINTS` видна по `0042F6BD–0042F6F0`. Для цивилизованных результат
`00538150` умножается на 365. Константа `E45E74` — float `365000.5`;
последовательность floor, преобразование в целое и деление произведения на 1000
даёт именно 365, а не округление дневного дохода до целых очков.
Это переменный лимит: он зависит от текущих эффектов и населения.

Следующий дневной вызов идёт через `00509F56–00509F68` в `00507770`.
Он находит первую активную запись исследования в `country+4C4`, проверяя
её байт `+1C`.

| Состояние | Действие дневного обновления |
|---|---|
| Нет активной технологии | Прибавляет дневной доход к запасу и обрезает результат до текущего лимита. Превышение теряется. |
| Есть активная технология | Передаёт запас вместе с дневным доходом в текущий проект, возвращает неиспользованный остаток в запас. Этот путь обходит ограничение запаса. |

Ключевые инструкции:

```asm
005077A6  jne 00507837                 ; найден активный проект
005077B6  add [esi+E3C],eax            ; без проекта: прибавить доход
0050780E  cmp [esi+E3C],eax            ; сравнить запас с лимитом
0050781A  mov [esi+E3C],eax            ; обрезать превышение

0050783A  add ecx,[esi+E3C]            ; с проектом: запас + доход
00507843  mov [esi+E3C],ebx            ; временно обнулить запас, ebx=0
0050785F  call 00579EE0                ; расход на текущий проект
00507869  add [esi+E3C],eax            ; вернуть остаток без clamp
```

Это **не мгновенное расходование всего запаса**. `00579EE0` применяет к проекту
не больше `MAX_DAILY_RESEARCH`, в этой сборке **100 RP за день**, и не больше
оставшейся стоимости технологии (`00579F2C–00579F69`). Остальное возвращается.
За один вызов завершается не более одной технологии: после её применения и
удаления проекта функция возвращается, не начинает следующий проект циклом.

Выбор технологии через `0058ADA0 → 00513930 → 00579E80` активирует проект и
не вызывает setter запаса. Следовательно, после вестернизации можно выбрать
исследование **до следующего дневного обновления** и постепенно использовать
сверхлимитный запас. После завершения технологии нужно выбрать следующую до
дня без активного исследования. Например, при запасе 20000 RP и доходе 10 RP/день
лимит равен 3650 RP; день без проекта оставит 3650, день с достаточно дорогим
проектом потратит 100 и оставит 19910 RP, даже несмотря на лимит 3650.
Это следствие двух ветвей кода; отдельный игровой опыт не проводился.
Посторонние эффекты изменения RP, использующие setter, могут отдельно вызвать
обрезание: активный проект не защищает от таких вмешательств.

## 2. Точный алгоритм выдачи технологий

Команда вестернизации вызывает `00542370` по `00588C6F`. Ниже описан именно
этот обработчик, а не предположение о любом скриптовом присваивании
`civilized = yes`.

### Список технологий и исходная таблица

1. Берётся менеджер технологий `[0125EADC]`. Создаётся временный массив уровней
   **с нулями**, а не копия собственных технологий (`005423D2–005423F9`).
2. Настоящие технологии группируются по `area`, поле объекта `+314`, в порядке
   их присутствия в менеджере (`00542460–00542555`). Общая категория army/navy
   и т. п. не является единицей этого прохода: единица — отдельная ветка `area`.
   Индекс технологии в таблице хранится в `+2E4`.
3. Проверка `vtable+20` отличает настоящую технологию от служебной пустой.
   У `CTechnology` это `00A31490`, `mov al,1; ret`; у `CNullTechnology` —
   `0058CFD0`, `xor al,al; ret`. Это не проверка доступности по году.

**Если страна в сфере:** по `country+142C` находится лидер сферы; значения его
таблицы `country+BCC → +2B8` копируются во временную таблицу для настоящих
технологий (`00542568–005425D4`). Это исходный набор, который ещё будет урезан.
Дыры лидера, если они есть, сохраняются; отсутствующие нижние технологии
автоматически не достраиваются.

**Если страна вне сферы:** для каждой ветки и каждой текущей великой державы
считается длина непрерывного начального набора изученных технологий. Подсчёт
останавливается на первом нулевом уровне. Берётся **минимум** этих длин.
Временный массив получает уровень 1 для этого общего префикса и 0 для остального
(`005425FD–005426C0`). Это не среднее и не количество технологий, изученных
большинством великих держав. Если хотя бы одна ВД не знает первую технологию
ветки, исходный набор этой ветки пуст.

Источник ВД — вектор `[012588E8]+BE0..BE4`. Его назначение подтверждается
обновлением великих держав `0068C5C0`: удаление старой ВД, изменение её флага
`country+31`, добавление новой по `0068C815`, затем `on_new_great_nation`.
Патологический случай пустого списка ВД: минимум остаётся равным полной длине
ветки, поэтому до последующего урезания выбрана вся ветка.

### Коэффициенты военных и экономических реформ

Для каждого типа реформ отдельно считается:

```text
A = сумма (индекс текущего варианта в категории + 1)
B = сумма числа всех вариантов соответствующих категорий
r = trunc(1000 × A / B)
f = MIN + trunc((MAX − MIN) × r / 1000)
```

Индексы начинаются с 0. Используются настоящие категории и варианты, прошедшие
виртуальные проверки; служебные NullIssueGroup/NullIssue пропускаются целиком.
Обычный исходный вариант `no_*` — настоящий вариант, поэтому **тоже даёт 1 в A**.
Здесь не суммируются `civilization_progress_modifier`, стоимость реформ или
процент вестернизации в интерфейсе.
Это подтверждается загрузчиком `00974AF0`: обычные имена вариантов создаются
через `009740B0`, который ставит vtable `00E36878` класса `CIssue`.
Её слот `+34` возвращает true; аналогично у обычной `CIssueGroup` слот `+18`
возвращает true. Специального исключения для имён `no_*` загрузчик не делает.

Экономические реформы считает `00547030` (`IssueManager+68`, `country+880`),
военные — `00547100` (`IssueManager+58`, `country+870`). В коде сами A/B
предварительно умножены на 1000; указанная формула точно сокращает этот общий
масштаб для штатных значений. Целочисленные деления отбрасывают дробную часть.

`MIN=150`, `MAX=600` в тысячных: это `UNCIV_TECH_SPREAD_MIN=0.15` и
`UNCIV_TECH_SPREAD_MAX=0.60` из действующего `common/defines.lua`.
Чтение этих полей в `defines.country+A8/+A4` — `0042EF01–0042EF60`.

В текущем `common/issues.txt` восемь военных категорий по два варианта и семь
экономических с суммарно 15 вариантами. Поэтому при всех исходных военных
вариантах получается `A/B=8/16`, `r=500`, `f=375`, то есть **37,5%**, а не 15%.
При всех исходных экономических вариантах `7/15 → r=466 → f=359`, то есть 35,9%.
Это иллюстрации формулы, не утверждение о возможности вестернизироваться со
всеми исходными вариантами сразу. Максимальные варианты дают `f=600`.

### Урезание исходного набора

Для каждой ветки:

1. Обратным проходом найти наибольший индекс `h` технологии с положительным
   временным уровнем. Если таких нет — ничего не делать (`005427A0–005427D8`).
2. По полю **этой технологии** `unciv_military` выбрать коэффициент:
   `yes` — военный, иначе экономический (`00542940–0054298E`). Это флаг в
   определении технологии, а не предположение по имени общей группы.
3. Вычислить предельный индекс `k`. Для штатных индексов этой сборки:

   ```text
   k = floor(h × f / 1000)
   ```

4. Обнулить уровни технологий с индексами `h,h−1,…,k+1`; значения индексов
   `0..k` оставить как были (`005429BA–005429E3`).

Таким образом, из сплошного исходного набора длины N остаётся
**`1 + floor((N−1) × f / 1000)`**, если N>0. Округляется индекс последней
технологии, а не количество технологий. Например, из шести технологий при
`f=600` останутся четыре: `1+floor(5×0.6)=4`. Непустой набор при штатном
неотрицательном коэффициенте сохраняет первую технологию. При дырках в наборе
лидера сферы формулу количества применять нельзя: нули остаются нулями.

Для побитового воспроизведения вычисления k:

```text
epsilon = 0.0005000000237487257
x = float32(float64(float32(h)) + epsilon)
y = float32(float64(x) * 1000.0)
t = int(floor(y))
k = trunc(trunc(t × f / 1000) / 1000)
```

Точная последовательность: `float32(h) → float64 → +double[E45840] → float32
→ float64 → ×double[E45660] → float32 → floor(00401000) → int(00B31C00)`.
Затем идут два целочисленных деления на 1000, второе реализовано умножением
на `10624DD3h` со сдвигами (`00542991–005429B0`). Для текущих малых индексов
`t=1000h`, поэтому простая формула выше точна.

### Применение результата

По `005427E8–0054286F` **вся временная таблица присваивается собственной**,
включая нулевые значения. Старые технологии не сохраняются посредством `max`:
они могут быть утрачены, если не входят в рассчитанный результат. Сравнение
старого и нового значения перед записью обслуживает сообщение, не защиту
старого уровня. Затем ставится civilized и выполняются пересчёты/on_civilize.

Выбор детерминированный. В этом обработчике нет случайного выбора, проверки
стоимости, списания RP, проверки текущего года или отдельного обхода графа
предпосылок. Порядок — порядок менеджера внутри каждой ветки; handler не
сортирует технологии по году. Текущие 150 технологий находятся в 25 ветках,
где годы фактически возрастают; 60 определений имеют `unciv_military=yes`.
Сам факт возрастающих годов в данных не является проверкой года в коде.
Загрузчик создаёт технологии последовательно по определениям: конструктор
`00577C55`, присваивание следующего ID `00577C5A`, добавление указателя в конец
вектора `00577DC5–00577DC7`, разбор определения `00577DE7`, связь с предыдущей
технологией той же области `00577E64`. Сортировки внутри этого прохода нет.

## 3. CreatineCore и воспроизведение

Действующий `creatinecore.dll` SHA256
`73857f40e2b6cde65fe35efe61db6d3d82ff2af037136f5e099101d50f960068`.
`PATCH_ALLOW_UNCIV_TECH_RESEARCH=0`. Активный `PATCH_CIVILIZE_NULL_CHECK=1`
в точке VA `0054248B` добавляет проверку результата поиска `area`: при null
пропускает технологию, при найденной категории воспроизводит обычные
инструкции. При корректных текущих определениях категорий это не меняет
описанный алгоритм. Комментарий upstream про «постройки» в этой функции
неточен: по машинному коду и RTTI здесь обрабатываются технологии.
Принадлежность поля `+38C` флагу `unciv_military` проверена по цепочке
строка `00E1D350` → регистрация токена `98A` (`00C521FE–00C52210`) →
обработчик `0056AEA4` → bool-парсер `0056AEAB`.

Для повторного получения свежего листинга с байтами и хешами диапазонов:

```powershell
python -B tools/engine_research/westernization_evidence.py --dumpbin <путь-к-dumpbin.exe> --output .work/westernization/evidence
```

Скрипт проверяет SHA256 EXE и не запускает игру. Крупные рабочие листинги
находятся в `.work/westernization/{evidence,rp,tech,audit}`. Для 13 ключевых
диапазонов RP свежий dumpbin также сопоставлен построчно с прежним полным
листингом; расхождений нет. Алгоритм технологий независимо проверен вторым
исследователем, включая RTTI, великие державы и разбор `unciv_military`.
Хеши извлечённых диапазонов и относящихся к выводу текущих данных сохранены в
[манифесте доказательств](westernization-engine-evidence.json).
