# Возврат из SP в главное меню в том же процессе

Исследование Victoria II HoD 3.04 из текущей сборки, 15–16 ноября 2026 года. SHA-256 `v2game.exe`: `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`. Адреса ниже — VA при image base `00400000`; в адаптере используются RVA. Источники — дизассемблирование этого EXE, GUI-файлы и журналы реального испытания PID 20056. Первый прогон прошёл подтверждение и экран итогов, но упал после создания нового главного меню. Исправление фазы выполнения, описанное ниже, пока требует повторного runtime-прогона.

## Выбранный механизм

Используется штатная цепочка кнопок игры, вызванных программно через уже квалифицированные `FindControl`/`Signal`. Это три самостоятельные мутации с отдельными наблюдениями состояния между ними:

1. На паузе открыть игровое меню штатным `0066EEE0`, затем вызвать `menu_panel/menu_resign_button`.
2. Найти зарегистрированный видимый диалог именно типа `RESIGN` и вызвать его `AgreeButton`.
3. Дождаться экрана итогов, вызвать `back_end/Exit`, затем дождаться нового объекта главного меню.

Вариант с прямой записью флага выхода короче, но обходит подтверждение и обычные подписчики GUI. Прямое освобождение мира, reset, завершение процесса и физический ввод для выбранного пути не нужны. `menu_quit_button` использовать нельзя: это другой запрос, завершающий приложение.

## Подтверждённые статические контракты

### Игровое меню и подтверждение

`interface/menubar.gui` содержит `menu_panel/menu_resign_button`, текст `MENU_BAR_GAME_RESIGN`, локальная позиция `{86,226}`; `menu_quit_button` расположен ниже и относится к выходу из приложения. Подтверждение использует `interface/eu3dialog.gui`, `DefaultDialog/AgreeButton`, текст `OK`; отмена — `DeclineButton`, текст `CANCEL`.

В `0066686F..006668EE` родитель `menu_panel` ищется у `[idler+1D24]` через virtual slot `6C`, кнопка `menu_resign_button` — через slot `34`. Сигнал кнопки расположен **встроенно** по `button+54`; native subscribe — virtual slot `4` у сигнала. Observer — `idler+4A8`; constructor в `0064AA31..0064AA43` задаёт ему callback `006766A0`, owner — `idler`.

`006766A0` — `void __thiscall(idler)`: выделяет объект размером `84`, создаёт диалог `00676240` с действием `RESIGN`, регистрирует его через `006480E0`, показывает через virtual slot `28`.

Диалог имеет vtable `00E0A7E4`, owner `dialog+8`, GUI-root `dialog+4`, finished-флаг `dialog+64`, обычную игровую строку действия по `dialog+68` (`length+78`, `capacity+7C`). `00640680` сохраняет owner и подписывает `AgreeButton` на observer `dialog+0C`: callback `00640B20`, owner `dialog`. `00640B20` переходит в virtual slot `18` диалога; у этой vtable это `00676500`.

`00676500` сравнивает действие с `RESIGN` и вызывает owner.virtual `114`; для точного игрового idler (vtable `00E0A34C`) это `0064EDC0`. Последний лишь записывает `byte[idler+1D21]=1` и возвращается. После callback диалог помечается finished. Для действия `QUIT` вызывается другой slot `110`, `0064EDB0`, флаг `1D20`.

Список диалогов подтверждён телом `006480E0`: head `idler+60`, tail `+64`, count `+68`; узел `{value+0, prev+4, next+8, ...}`, размер `10`. Его можно обойти с ограничением числа узлов и защитой от циклов, не сканируя память мира. Одного совпадения vtable недостаточно: необходимо проверить owner, действие `RESIGN`, unfinished и видимость `byte[GUI-root+67]`.

### Экран итогов после завершения партии

`00656676` проверяет флаг `1D21`; SP-ветка начинается с `006567E1`. Она создаёт новый экран через `005F8110` и штатно заменяет текущий idler через `009DF260`. Это **промежуточный экран итогов**, а не уже готовое главное меню.

Новый объект имеет vtable `00E04CFC`. Его поля: owner game по `+A0`, GUI-panel по `+A8`. Constructor `005F8285..005F8291` вызывает `00682B40(world)` с новым объектом в `EDI`; `00682B47` записывает объект в `world+B24`. Поэтому для наблюдения следующей стадии достаточно заново читать текущий world/idler, не сохранять освобождённый старый idler.

`005F9260` создаёт панель `back_end` из `interface/backend.gui`; `005F9347..005F936B` находит кнопку `Exit` virtual slot `34` и подписывает observer `summary+5B0`. Constructor `005F81DA..005F81E8` задаёт callback `005FB560`, owner — сам экран. В GUI кнопка подписана `EXIT`, позиция `{682,938}`. Эту кнопку не следует путать с `endgame_dialog/quit_button` из `menubar.gui`.

`005FB560` — `void __thiscall(summary)`: вызывает обычные операции завершения текущей партии, создаёт `CFrontEnd` через `00754A00` (`005FB619`), записывает pending idler в `game+E0`. Constructor hook `MenuCtor` моста уже перехватывает именно `00754A00`; новый объект должен быть доступен как `mainMenu`, его vtable — `base+A13DBC`. Сам constructor capture ещё не является ACK активации. Callback может инициировать уничтожение старого экрана; после `Signal` читать его поля нельзя.

Уточнение по runtime и найденному native writer: контекст `[campaign_idler+17E8]` имеет vtable `base+A0845C`. **Активный idler находится в `context+84`; `context+E0` — только ожидающая замена.** `009DF4DB` читает pending `+E0`, `009DF4E1` обнуляет его, `009DF4E7..009DF4FB` освобождает прежний active `+84`, `009DF4FD` записывает новый active `+84` и вызывает его штатную инициализацию. Начальный guard `context+E0 == campaign_idler` был неверен: в обычной кампании `E0=0`. Теперь адаптер проверяет класс контекста и `context+84 == world+B24`. ACK итогов и нового главного меню также требует `+84`; переходное состояние после constructor с ещё не активированным pending требует дальнейшего read-only poll.

## Кандидат адаптера и интеграция

Адаптер `tools/vic2test/native/sp_frontend.h` интегрирован в bridge. Он использует существующие read guards, `Control`/`Press`, ABI GPC status и квалифицированный вызов `66EEE0` из `mp_save.h`. Изменение от 16 ноября также переносит выполнение последнего callback в хвост штатного обновления экрана итогов.

Интерфейс:

```cpp
Ticket RequestResign(DWORD base);
State Inspect(DWORD base, const Ticket&, DWORD capturedMainMenu);
void ConfirmResign(DWORD base, const Ticket&);
void ExitSummary(DWORD base, const Ticket&, bool afterSummaryUpdate = false);
```

`Ticket` ограничен одним возвратом в меню и содержит идентичности world/idler/game и дату, а не сохраняемый контекст следующей кампании. Начальный запрос требует точный SP idler, паузу, отсутствие `manager.executing` и отсутствие чужих modal/settings/save окон. Если установлен GPC runtime, требуется `busy=0`, а при включённой механике — успешное завершение callback для текущей даты. В адаптере проверяются исходные подписи, callback owners/addresses и релевантные vtable slots.

Bridge дополнительно обязан запретить запрос при pending advance/event/save/MP-команде и обеспечить выполнение на owner thread. Состояния контроллера: `request_sent → confirmation_observed → confirm_sent → summary_observed → exit_sent → new_main_menu_observed`. Каждый native callback отправляется ровно один раз; `queued` подтверждает только отправку. Ошибка после начала мутации — `E_SP_FRONTEND_OUTCOME_UNKNOWN`, повтор запрещён. Между стадиями разрешено только наблюдение. При timeout незавершённый переход нельзя объявлять успешным.

### Отказ первого прогона и квалифицированная фаза Exit

В прогоне PID 20056, owner thread 9212, последовательность `RESIGN → подтверждение → summary` завершилась ожидаемо. На `sp-return-exit` hook захватил новый `CFrontEnd` `24E5E140`; bridge ответил `pending=true`, затем процесс упал с `C0000005`. Runtime image base `00A60000`, EIP `00C58785`, то есть RVA `1F8785` / preferred VA `005F8785`. В стеке — native owner-loop `009DF966`; объект в `EDI` всё ещё `CBackEndIdler`. Невалидный vtable `6974706F` — первые байты ASCII `options`, а не адрес объекта. Артефакты: `.work/gpc-acceptance/.work/sp-return-qualification-01.json`, `gpc-probe2/game/z_CreatineCore/Logs/v2dll_crash.log` и основной журнал соответствующего PID.

`005F8470` — `CBackEndIdler::Update`, vtable `00E04CFC`, slot `4`. ABI: `void __thiscall(this,unsigned tick)`; caller передаёт `push 1`, функция заканчивается `ret 4` в `005F8AA2`. Внутри Update, `005F8744..005F8788`, выполняется поиск `options` через старый GUI-root `[backend+8C]`; именно здесь упал прогон. Последний callback уже создал новый frontend и изменил GUI-состояние, но движок ещё выполнял обновление старого backend.

Native loop `009DF953..009DF964` вызывает активный idler Update, и **только затем**, начиная с `009DF966`, проверяет pending switch. Произвольная точка `PeekMessageA`/`GetMessageA` не даёт гарантии, что старый Update уже завершён: callback мог исполниться перед этим Update или при вложенной обработке сообщений внутри него. Журнал/stack не позволяют различить эти два варианта; оба несовместимы с синхронным созданием нового GUI до окончания старого Update. Это дефект фазы bridge, а не основание ослаблять проверки идентичности объектов или скрывать AV.

Исправление: bridge устанавливает wrapper ровно slot `1` vtable `A04CFC` через существующий `PatchSlot`. Wrapper сначала вызывает исходный `005F8470` с неизменёнными аргументами, затем на owner thread исполняет `Pump` с признаком безопасной фазы. До этой фазы `sp-return-exit` остаётся в IPC state `1` и не получает ложного ACK. Остальные команды сохраняют прежний механизм выполнения. После callback wrapper больше не читает backend; управление возвращается непосредственно в native loop, который активирует новый pending frontend. `ExitSummary` отказывает с `E_SP_FRONTEND_UNSAFE_PHASE`, если признак фазы отсутствует.

Перед установкой проверяются исходный vtable slot, пролог Update, `ret 4` и 26 байтов native caller с порядком `Update → pending check`. В диагностике установки появляется `vic2test: SP return Exit поставлен после CBackEndIdler::Update`. Проверка всех этих байтов против точного EXE выполнена статически; новый runtime-прогон остаётся обязательным. Это изменение не перехватывает освобождение мира и не меняет native callback `005FB560`.

`Inspect` считает главное меню завершённым только при совпадении нового захваченного объекта с `game+84`; старый frontend не является ACK. После этого контроллер уничтожает ticket и сбрасывает старые event/popup pointers, pending commands, advance target. Новый `open-single-player/load-save/play` работает уже с новыми constructor captures. Не разыменовывать прежний `world+B24` после загрузки другого сейва.

`consoleManager` также не имеет lifetime всего процесса. `00667A76` выделяет новый console object размером `4C`; `00667AA6` вызывает его constructor `00613380`, а `00667AB8` сохраняет объект в `campaign_idler+1D0C`. Constructor `00613822..00613845` выделяет vector header размером `10`, сохраняет его в `console+48` и заполняет через `00423990`; `ConsoleTail` на `00423A43` захватывает именно этот vector header в `ESI`. Следовательно, старый capture нельзя переносить в новую кампанию. После загрузки допустим новый constructor capture либо проверенное повторное получение `[[new_idler+1D0C]+48]` с обычной проверкой границ вектора и наличия команд `event`/`save`. Сброс без нового capture/reacquire оставил бы консоль недоступной; оставление старого указателя создало бы обращение к освобождённому объекту.

## Проверки, которые остаются главному агенту

16 ноября исправленный мост прошёл реальный прогон PID 12536: три перехода
1836 → 1931 → 1841 → 1836 без завершения процесса. Каждый возврат получил
`main_menu=true`, каждая загрузка — новый `console_captured=true` и нужную дату.
После первого дня каждой кампании восстановлены её собственные pass/RNG/checksum;
preview дал соответственно 0, 0 и 56 пар до повторной выдачи в сценарии 1836.
Артефакт: `.work/gpc-artifacts/sp-return-qualification-02.json`.
Ниже сохранена подробная программа для последующих регрессий.

1. Собрать bridge с кандидатом; подтвердить два отказа до мутации: MP и SP без паузы.
2. В paused SP после завершённого GPC callback отправить RequestResign, проверить сохранение PID, даты и появление именно `RESIGN`.
3. Отправить ConfirmResign один раз; read-only poll должен увидеть смену idler на vtable `base+A04CFC`, тот же game owner и видимый `back_end`.
4. Отправить ExitSummary один раз; дождаться нового `CaptureMenu`, vtable `base+A13DBC`, `game+84 == mainMenu`, прежний PID жив. Отдельно подтвердить, что процесс не завершился.
5. Загрузить другой сейв существующими командами; подтвердить новую дату, новый console capture, GPC scheduler/cache от нового мира и отсутствие утечки старых флагов/кэша. Выполнить минимум три цикла и сравнить результаты oracle.

Статический анализ квалифицирует адреса, ABI и штатную цепочку; первый runtime-прогон выявил дефект фазы последнего callback, а повторный подтвердил исправленные возвраты и загрузки. Отдельные отрицательные проверки MP/непаузы не подменяются этим положительным прогоном. Ручной GUI-сценарий для дополнительной квалификации совпадает с цепочкой `menu_resign_button → AgreeButton → back_end/Exit`; координаты на экране заранее не фиксируются.
