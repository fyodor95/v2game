# Определение текущего сетевого режима Victoria II

Дата: 15 ноября 2026 года. Исследование только статическое: игра, GUI, сборки и Git не запускались. Изменён только этот отчёт. Источник — текущий `v2game.exe`, SHA-256 `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`, и существующее `.work/creatinecore/game-disassembly.txt`.

Адреса VA ниже рассчитаны на базу `00400000`. Runtime использует действительную базу образа плюс RVA. Номера строк относятся к дизассемблированию указанного EXE.

## Вывод для запрета локальных мутаций CLI

У игры уже есть собственный запрет консольных команд в MP. Он проверяет **байт `current_idler+0x5C`**, а не роль сервера или количество людей. Для CLI рекомендуется повторить именно эту проверку, предварительно подтвердив текущий тип idler и сигнатуры EXE.

Признак относится к текущему объекту игровой сессии. Он не является sticky-переменной DLL. Значение `0` означает разрешённую одиночную ветку штатного консольного диспетчера, ненулевое — отказ с `No cheats in MP`. Для нового адаптера значение, отличное от `0` и `1`, следует считать повреждением/неизвестным режимом и запрещать мутации.

Это сильное статическое доказательство назначения поля. Отдельный runtime-прогон SP, MP host и MP client ещё необходим: данный отчёт не объявляет его выполненным.

## 1. Прямое доказательство: штатный запрет `No cheats in MP`

Консольный обработчик `00613AA0` (около строки 679648):

```text
00613AE7  xor ebx,ebx
...
00613CA0  mov eax,[012588E8]       ; текущий world
00613CB1  mov eax,[eax+0xB24]      ; текущий idler
00613CB7  cmp byte ptr [eax+0x5C],bl
00613CBA  je 00613D1B             ; ноль: продолжить разбор команды
00613CBD  push 00E05B8C           ; литерал "No cheats in MP"
```

Ненулевая ветка выводит отказ через `006138F0` и переходит к завершению обработки; нормальный разбор команды начинается в `00613D1B`.

Точные позиции: `00613CB1` — строка 679787, проверка — 679788, ссылка на текст — 679791. Наличие читаемого литерала и непосредственно управляющего ветвления снимает необходимость угадывать значение поля по имени структуры.

Проверяемая последовательность без абсолютных адресов, `RVA 00213CB1`:

```text
8B 80 24 0B 00 00 38 58 5C 74 5F
```

Следующий `push` содержит relocatable адрес литерала; при его проверке надо сравнивать `actual_base+0xA05B8C`, а не исходный VA.

## 2. Создание и срок жизни признака

Базовый конструктор idler `00647D30` в `00647D86` обнуляет `idler+0x5C` (строка 741719).

Конструктор `CInGameIdler` — `0064A6D0` (строка 745021). Он устанавливает vtable `00E0A34C` в `0064A744` и затем записывает режим:

```text
0064BD21  mov al,[ebp+0x18]       ; пятый стековый аргумент конструктора
0064BD24  mov edx,[012588E8]
0064BD2A  mov [edx+0xBB8],al
0064BD30  mov [ebx+0x5C],al       ; ebx = создаваемый CInGameIdler
```

Это строки 747283–747286. Последняя запись не привязана к тому, отправлял ли процесс когда-либо серверный пакет. Новый объект получает признак из текущего пути создания кампании.

Единственный прямой вызывающий участок этого конструктора в данном дизассемблировании — `00757FA6` (строка 1072787). В `00757F82` (1072774) он читает байт `front_end_state+0x5C`, передаёт его пятым аргументом, а затем создаёт новый игровой idler. Текущий MP-режим таким образом передаётся из frontend в игровую сессию.

`world+0xBB8` получает то же значение в показанном участке. Для CLI всё же предпочтительно читать `idler+0x5C`: именно это поле выбирает отказ штатной консоли, а его lifetime ограничен текущим idler. Совпадение двух полей удобно логировать как дополнительную runtime-проверку, не превращая неподтверждённый второй признак в самостоятельное разрешение.

## 3. Проверка типа idler и получение session manager

Текущий idler находится в `*(*(base+0xE588E8)+0xB24)`.

Квалифицированная vtable `CInGameIdler` — `base+0xA0A34C`. RTTI-имя — `.?AVCInGameIdler@@`. Существующий CLI-мост проверяет его через vtable locator в `tools/vic2test/native/bridge.cpp`, функция `InCampaign`. При точном EXE и неизменённой vtable проверка самого адреса проще и строже. Клонированную или неизвестную vtable нельзя считать подходящей только потому, что по смещению `+0x5C` удалось прочитать ноль.

Виртуальный слот `0x44` (`17`) этой vtable содержит `00651D10` (`RVA 00251D10`, строка 754731):

```text
00651D10  mov eax,[ecx+0x17E8]
00651D16  mov eax,[eax+0x12C]
00651D1C  ret
```

Это подтверждённый accessor session manager для игрового idler, `__thiscall`, без стековых аргументов. Для чтения режима CLI вызов accessor вообще не нужен; он полезен для диагностического снимка роли и состояния command execution.

Сигнатура accessor без абсолютных адресов:

```text
8B 81 E8 17 00 00 8B 80 2C 01 00 00 C3
```

В upstream `Source/v2dll_country_daily_optimizer/tgl_patch/src/game/world.h` уже зафиксированы:

- `session_manager+0x34`: признак server; `1` встречается и в SP, и у MP host.
- `session_manager+0x234`: выполнение команды, включая часовой игровой тик.
- `session_manager+0x38`: очередь команд, используемая `CEvent::run` и другими обычными действиями.

Существование очереди не отличает MP от SP. Понятие server тоже не равно multiplayer. Для диагностики можно дополнительно записывать пару `(idler_mode, manager_server)`: ожидаются SP `(0,1)`, MP host `(1,1)`, MP client `(1,0)`. Эти комбинации предстоит подтвердить на двух настоящих участниках; само разрешение локальных мутаций не должно зависеть только от второй координаты.

## 4. Почему другие признаки не подходят

`V2TechButton.cpp:13464` объявляет `g_mpServerSeen`. Хук `FUN_00A62EA0` отмечает отправку серверного пакета через `MarkServerSide`; переменная становится `1` и не отражает последующую смену кампании. Клиент может всю партию оставаться с `0`. Она пригодна для узкой диагностики host-ветки upstream, но не для разрешения CLI.

`world+0x2C == 4` upstream использует как состояние работающей партии, когда запрещена повторная синхронизация контролёров. Это стадия сессии, а не признак сетевого режима.

Количество элементов human vector `world+0xAEC/+0xAF0`, количество ненулевых людей, существование session manager и ненулевой player ID также не заменяют mode: сервер может ещё находиться один в лобби, а отключение клиента не делает MP host одиночной сессией.

## 5. Рекомендуемый контракт CLI

Ввести три результата чтения режима: `Unknown`, `SinglePlayer`, `Multiplayer`.

Перед любой локальной мутацией:

1. Проверить сигнатуры текущего EXE, читаемый текущий world и игровой idler.
2. Проверить vtable `CInGameIdler` либо отдельно квалифицированную совместимую обёртку.
3. Прочитать `idler+0x5C`; `0` даёт SP, `1` даёт MP, прочее — Unknown.
4. Разрешить локальную тестовую мутацию только при SP и остальных существующих ограничениях изолированного теста.
5. В MP и Unknown вернуть явный отказ до изменения мира, RNG, скоростей, паузы, очереди или механического состояния.

Проверку выполнять заново при каждом запросе; не кэшировать idler, session manager или результат по PID. Вне кампании `Unknown` не является разрешением. Read-only `status`/`preview`/`snapshot` можно оставить доступными при остальных необходимых проверках.

Область запрета охватывает не только новую `culture-cores run`: старые локальные `advance`, `event-fire*`, выбор опции через мост, выполнение решения, локальный вызов паузы/скорости и `--auto-events` способны менять сетевую симуляцию или обходить штатный UI. Для настоящего MP-стенда ими нельзя управлять ходом партии; используются обычные действия соответствующих окон. Возможность чтения либо технической записи диагностического файла не равна разрешению вызвать native save/load в любой фазе.

Runtime-проверки: SP → MP host → MP client → выход в меню → новая SP в том же процессе; MP host без подключённых клиентов; потеря клиента; перехост; меню/загрузка/неизвестная vtable. Зафиксировать mode, тип idler, manager server и executing flag, затем убедиться в отказе **до** любой мутации. Сравнить результат с нативной консольной веткой `No cheats in MP`, не применяя чит к реальной сетевой партии.

## 6. Данные для GUI-стенда и ограничения исследования

В `interface/temp_frontend.gui` найдены действительные имена элементов:

- `multiplayer_menu`: `host`, `join`, `join_direct`, `scan`, `playername`.
- `multiplayer_connect_menu`: `info_list`, `back`.
- Имена стран/готовности относятся к отдельному lobby GUI.

Это идентификаторы из текущих файлов, не экспортированный API кликов. Координаты в `.gui` относительные; их нельзя напрямую выдавать за физические координаты рабочего стола при DPI 200%.

Номер рабочего порта здесь не квалифицирован. В низкоуровневых сетевых конструкторах `00A73670` и `00A748D0` есть исходное значение `0x662`, а `00A73730` передаёт поле через преобразование сетевого порядка байтов. Не установлено, какой вызывающий участок меняет это поле для конкретной игровой сессии; поэтому выводить из одной константы утверждение о фактическом игровом порте нельзя. Для запущенного GUI-стенда нужно наблюдать реальные endpoints его PID, не меняя системные правила сети на основании предположения.
