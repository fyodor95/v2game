Да. Причём сейчас есть несколько проектов именно вокруг **оригинального `v2game.exe` Victoria 2**, а не его переимплементации. Для твоей цели самый интересный — **Smedley**.

### Smedley — почти ровно то, что ты ищешь

**Smedley** позиционируется как *API and plugin loader for Victoria 2*, по аналогии с Minecraft Forge. Его launcher запускает оригинальный Victoria 2 и **инжектит DLL kernel + пользовательские DLL-плагины**. Главное — плагины работают не через обычные Vic2 `effects/triggers`, а получают доступ к реальным объектам игры. [GitHub](https://github.com/shenso/smedley_kernel?utm_source=chatgpt.com)

[Smedley Kernel на GitHub](https://github.com/shenso/smedley_kernel?utm_source=chatgpt.com)

Это не просто эксперимент: в июле–сентябре 2026 года появился мод **AI army control toggle / AI Assist**, который использует Smedley для управления армиями игрока через внутренний API; более поздняя версия также автоматизирует строительство фабрик и инвестиции. То есть DLL-инъекция по-прежнему практически используется с оригинальной Victoria 2. [ModDB](https://www.moddb.com/mods/ai-army-control-toggle?utm_source=chatgpt.com)

Есть, однако, два нюанса.

Первый: оригинальный репозиторий Smedley был **архивирован 28 мая 2025 года**. [GitHub](https://github.com/shenso/smedley_kernel?utm_source=chatgpt.com)

Второй: готового Python/Lua scripting API там, судя по документации, нет. Автор прямо писал, что *в будущем* хотел использовать встроенный Lua runtime игры для sandboxed plugins. То есть основной интерфейс Smedley — **нативные DLL-плагины**, а не скрипты. [GitHub](https://github.com/shenso/smedley_kernel)

Но для твоей задачи это уже почти достаточная инфраструктура.

### Victoria2-Reverse-Engineering — сейчас активно развивается

Есть совсем свежий проект:

[maxioten/Victoria2-Reverse-Engineering](https://github.com/maxioten/Victoria2-Reverse-Engineering?utm_source=chatgpt.com)

Он занимается именно **статическим reverse engineering `v2game.exe` через Ghidra**. На сентябрь 2026 года там уже документированы:

- main loop;
- economy/market;
- AI;
- event system;
- research;
- game speed;
- RNG;
- initialization;
- UI callbacks;
- console;
- часть внутренних структур и адресов.

Например, авторы уже нашли обработчик консольных команд — `console_commands` по адресу `0x00420EB0`. Он получает токенизированный текст команды и дальше dispatch'ит его по строкам команд. Они экспериментально проверили, что при отключении этой функции пропадают все console commands. [GitHub](https://github.com/maxioten/Victoria2-Reverse-Engineering)

Это **очень интересно именно для программного управления**.

Теоретически можно сделать:

```text
Python
   ¦
   ¦ named pipe / TCP / shared memory
   Ў
my_vic2_bridge.dll
   ¦
   ¦ вызов функции оригинального движка
   Ў
console_commands(...)
   ¦
   Ў
Victoria 2
```

И тогда Python, например, отправляет:

```python
vic.command("money 1000")
vic.command("event 12345")
vic.command("tag FRA")
```

без открытия консоли, эмуляции клавиатуры и вообще без GUI.

Для более сложных действий bridge DLL может не вызывать консоль, а непосредственно дергать найденные функции движка.

### А что со встроенным Lua?

У Victoria 2 действительно есть `lua5.1.dll` / `lua51.dll`. Это не случайность: в движке присутствует Lua runtime. [PCGamingWiki](https://www.pcgamingwiki.com/wiki/Victoria_II?utm_source=chatgpt.com)

Но **готового Lua API вида**

```lua
country = vic2.get_country("RUS")
country:build_factory(...)
```

у оригинальной игры, насколько я смог найти, нет.

Более того, сам разработчик Smedley писал:

> I may try to leverage the game's lua runtime...

то есть даже он рассматривал подключение Lua как будущую возможность, а не как уже существующий удобный API. [GitHub](https://github.com/shenso/smedley_kernel)

В 2020 году Paradox также отдельно обновила Lua-библиотеки Victoria 2, отключив `luaopen_io` и `luaopen_os` из соображений безопасности. Это подтверждает наличие Lua VM, но не наличие полноценного публичного game-control API. [SteamDB](https://steamdb.info/patchnotes/4667422/?utm_source=chatgpt.com)

## Что я бы использовал для твоей задачи

Если цель примерно такая:

```python
game = Victoria2()

game.pause()
game.select_country("RUS")

game.set_tax_rate("poor", 0.40)
game.set_national_focus(123, "clergy")
game.build_factory(state=42, factory="steel_factory")

game.run(days=30)

print(game.country("RUS").treasury)
```

то **переписывать игру как Project Alice вообще не требуется**.

Самый реалистичный путь сейчас выглядит так:

```text
             Victoria 2 original
                   ¦
            v2game.exe 3.04
                   ¦
         ----------+---------¬
         ¦ DLL injection     ¦
         Ў                   Ў
     Smedley          RE/custom DLL
         ¦                   ¦
         L---------T----------
                   ¦
             bridge.dll
                   ¦
        Named Pipe / TCP
                   ¦
             Python API
```

Причём первая версия bridge может быть **совсем маленькой**. Не надо сразу reverse-engineer'ить строительство, дипломатию и армии.

Достаточно сначала экспортировать примерно:

```text
pause()
unpause()
set_speed(n)

console(string)

get_date()
get_player_country()
get_country_money(tag)
get_country_prestige(tag)

save_game()
```

Самое интересное здесь то, что наличие уже разобранного `console_commands()` резко облегчает bootstrap. Получается программная консоль Victoria 2 **без клавиатуры и GUI**.

А затем по мере необходимости можно добавлять настоящие вызовы внутренних функций:

```text
set_national_focus(...)
move_army(...)
construct_factory(...)
declare_war(...)
set_budget_slider(...)
```

и тем самым постепенно получить что-то вроде **headless-ish API к оригинальной Victoria 2**.

Я бы сейчас в первую очередь копал связку **Smedley + свежий Victoria2-Reverse-Engineering + V2 Custom DLL**. Из найденного это существенно ближе к твоей задаче, чем Project Alice. И, учитывая что ты работаешь с C++, написать поверх этого небольшой `vic2_bridge.dll` с IPC-интерфейсом для Python выглядит вполне реалистичным проектом. [GitHub](https://github.com/shenso/smedley_kernel?utm_source=chatgpt.com)

**Шаг 1. Скачай базовый комплект**

[Полная версия 0.6 (377 МБ)](https://www.moddb.com/mods/victoria-2-unofficial-patch-305/downloads/victoria-2-unofficial-patch-305-06?utm_source=chatgpt.com)

Также есть более поздний крупный архив [0.7.2 (293 МБ)](https://www.moddb.com/mods/victoria-2-unofficial-patch-305/downloads/victoria-2-unofficial-patch-305-072?utm_source=chatgpt.com). Для нового развёртывания имеет смысл проверить его состав: возможно, он уже содержит всю необходимую базу.

**Шаг 2. Размести мод в каталоге игры**

По инструкции автора в `Victoria 2/mod/` должны попасть два каталога и один файл:

```
Victoria 2/
L-- mod/
    +-- Victoria 2 unofficial patch 3.05/
    +-- Patch 3.05/
    L-- Patch 3.05.mod
```

Сохрани внутреннюю структуру архива, не создавая лишних вложенных папок.

**Шаг 3. Примени обновление v0.8.2**

[Скачать v0.8.2](https://www.moddb.com/mods/victoria-2-unofficial-patch-305/downloads/victoria-2-unofficial-patch-305-082?utm_source=chatgpt.com)

Это обновление необходимо накладывать поверх подходящего базового комплекта, сохраняя относительные пути файлов. Однако автор не опубликовал достаточно ясной инструкции по переходу с 0.6/0.7.2 на 0.8.2, поэтому я не могу гарантировать, что достаточно просто заменить файлы из двух архивов. Прежде чем объединять их, проверь, какие каталоги и исполняемые компоненты содержит v0.8.2.

**Шаг 4. Запусти игру с патчем**

В исходной инструкции требуется выбрать только `Patch 3.05` в лаунчере Victoria 2, без дополнительных модов. При первом запуске система создаёт отдельную модифицированную установку, используя твои оригинальные `v2game.exe` и `victoria2.exe`.

Для Steam-версии автор также указывает запуск через `start_patch_steam_version.bat` в корневой папке игры. В более новых сборках способ запуска мог измениться, так что при наличии инструкции внутри архива приоритет у неё.

Дополнительные моды, например GFM, устанавливаются в отдельный каталог `mod` модифицированной версии. Совместимость с ними нужно проверять отдельно.

## **4. Есть и более свежая разработка — CreatineCore**

Здесь обнаружилось важное обновление: проект V2DLL теперь называется **CreatineCore Modding Toolkit**. Его разработчики прямо называют его преемником V2DLL / Unofficial Patch 3.05.

[CreatineCore — репозиторий и подробное описание возможностей](https://github.com/artyom-kuznetsov/V2DLL_Victoria-2-Extension?utm_source=chatgpt.com)

В отличие от исторического способа установки 3.05 через отдельный мод, **актуальная инструкция CreatineCore предлагает установку непосредственно в каталог оригинальной игры**:

1. Скопировать файлы сборки CreatineCore в папку, содержащую `v2game.exe`.
2. Открыть `z_CreatineCore` и настроить `creatinecore_dll_settings.ini` (в некоторых версиях имя конфигурационного файла отличается).
3. Запускать игру обычным способом.

В репозитории сейчас есть каталог `CREATINECORE_LATEST_BUILD`; в README он назван `CreatineCore_LATEST_INSTALL`. Это расхождение в названиях, поэтому перед установкой стоит проверить структуру самого каталога.

Такой способ проще для применения исправлений к обычной Victoria 2 и существующим модам. Но я бы использовал **отдельную копию установки игры**, поскольку DLL загрузчика затрагивает всё окружение. Не стоит совмещать эту сборку с установленной через ModDB 3.05, не проверив версии общих библиотек.

Есть даже функция, которая появилась **позже последнего релиза 0.8.2 на ModDB**.

5 ноября 2026 года разработчик CreatineCore сообщил о реализации `ACTIVATE_DEACTIVATE_UNIT`: эта функция позволяет активировать и отключать типы войск через технологии, события, решения и консольные команды. Она уже была доступна в актуальной сборке GitHub, но её включение в следующий официальный пакет ещё планировалось.&#x20;

## **1. Настройка CreatineCore: сначала исправления, потом экономика**

Я проверил конфигурационные файлы актуальной сборки. Важная поправка к предыдущему ответу: файл в самом GitHub-архиве называется `z_CreatineCore/creatinecore_settings.ini`. В README встречается другое, устаревшее имя.

### **1.1. Выбери консервативные исправления**

Для первого запуска я бы оставил следующие опции включёнными:

| Настройка                        | Для чего                                                        |
| -------------------------------- | --------------------------------------------------------------- |
| `ARMY_FIX_BAD_REINFORCEMENT`     | Исправление неправильного пополнения армий                      |
| `NAVY_FIX_BAD_REINFORCEMENT`     | Аналогичное исправление для флотов                              |
| `PATCH_CIVILIZE_NULL_CHECK`      | Защита от некорректного доступа к данным при цивилизации страны |
| `FIX_MEMORY_MISS_CRASHES`        | Исправления определённых обращений к памяти                     |
| `PATCH_TECH_NULL_CHECK_FIXES`    | Защита от ошибок с отсутствующими объектами технологий          |
| `PATCH_SUPPLY_SOURCE_NULL_CHECK` | Защита от ошибок с отсутствующим источником ресурсов            |

Уже после проверки я бы добавлял исправления, которые изменяют результаты симуляции: `FACTORY_AI_SPAM_FIX`, `POP_FIX_NEEDS_MODIFIERS`, `FACTORY_SUBSIDY_COVERS_TARIFF` и другие.

Они действительно направлены на устранение проблем, но это не значит, что их включение оставит игровой мир неизменным. Например, исправленный AI может принимать другие решения, а исправленные выплаты населению повлияют на экономику.

### **1.2. Ускорение: сначала без многопоточности**

В `creatinecore_settings.ini` предлагаю такой первоначальный набор:

```
PATCH_COMPRESS_FLAG_CACHE=1
PATCH_PREFETCH_POPS=1
PATCH_PREFETCH_RELATIONS=1
PATCH_PREFETCH_AI_RELATIONS=1
PATCH_CULL_DECISION_CHECKS=1
PATCH_CULL_CB_CHECKS=1

PATCH_FAST_AI_QUEUE=0
PATCH_PARALLEL_DECISIONS=0
PATCH_PARALLEL_EVENTS=0

ENABLE_LOG=1
DEBUG_LOG=0
```

Первые шесть настроек — хорошие кандидаты на ускорение без преднамеренного изменения правил игры. При этом `CULL_*` необходимо проверять на твоём моде: неправильное отсечение условия способно изменить поведение AI.

Три последние оптимизации симуляции я временно отключаю не потому, что они заведомо плохие, а чтобы исключить влияние порядка выполнения задач и многопоточности при первоначальном сравнении.

Есть ещё **второй файл настроек**:

`z_CreatineCore/dll_Submods/ccore_performance_patch.ini`

В нём по умолчанию включено:

```
PATCH_POP_QUANTIZE=1
POP_QUANTIZE_KEEP_BITS=12
```

Это округление дробных частей денег/потребностей POP. Для твоей задачи я бы обязательно начал с:

```
PATCH_POP_QUANTIZE=0
```

Потому что квантование — уже изменение численного поведения симуляции, а не только ускорение.

### **1.3. Новое ценообразование**

В CreatineCore есть два алгоритма:

| Параметр                           | Поведение                                                             |
| ---------------------------------- | --------------------------------------------------------------------- |
| `TRADE_PRICE_DELTA_PERCENTUAL=1`   | Шаг изменения цены примерно 0,25% от текущей цены за день             |
| `TRADE_PRICE_DELTA_EXPONENTIAL=1`  | Альтернативный алгоритм изменения шага цены, реализованный Vesper     |
| `TRADE_MAX_PRICE_20X_MULTIPLIER=1` | Расширяет максимальную цену товара; потенциально опасен для экономики |

Оба первых варианта заменяют стандартный абсолютный шаг 0,01, но **не должны включаться одновременно**. В техническом описании указано, что при включении обоих приоритет имеет экспоненциальный.

Я бы начал с процентного алгоритма:

```
TRADE_PRICE_DELTA_PERCENTUAL=1
TRADE_PRICE_DELTA_EXPONENTIAL=0
TRADE_MAX_PRICE_20X_MULTIPLIER=0
```

Это самостоятельное изменение игровых правил, поэтому включать его лучше только после теста ускорений и исправлений.

Есть ещё существенное расхождение в документации: README описывает процентное изменение как долю базовой цены, а техническое описание патча — как долю текущей цены. Для расчёта поведения я бы ориентировался на техническую реализацию, но перед окончательным выбором проверил динамику нескольких товаров в игре.

Ещё серьёзнее расхождение у `TRADE_MAX_PRICE_20X_MULTIPLIER`: по анализу фактически записываемых байтов его величина не соответствует названию и README. Поэтому **ценовой потолок пока не расширяем**, тем более что автор предупреждает о риске переполнения фабричных накоплений.&#x20;

### **Smedley уже умеет управлять запуском игры через CLI**

Речь о [adrunkhuman/smedley_kernel](https://github.com/adrunkhuman/smedley_kernel?utm_source=chatgpt.com).

В этой версии реализованы:

- `smedley_cli.exe` — запуск игры из терминала;
- `campaign_runner` — автоматическая загрузка сохранения, управление скоростью, паузой и прохождение заданного числа дней;
- `telemetry` — запись состояния игры в JSONL;
- `smedley_trace.exe` — анализ и сравнение результатов;
- `scripting` — выполнение ограниченных Lua 5.1-скриптов.

Например, документация предусматривает такой запуск:

```
smedley_cli `
  --game-dir "C:\Vic2\Test" `
  --plugin plugins\campaign_runner.toml `
  --plugin plugins\telemetry.toml `
  --save "C:\Vic2\Saves\baseline.v2" `
  --speed 5 `
  --run-days 30 `
  --quit-after-run `
  --telemetry `
  --telemetry-output "C:\Vic2\Reports\run.jsonl"
```

Это документированный интерфейс Smedley: он загружает сохранение, запускает симуляцию на 30 игровых дней и собирает телеметрию. При этом Smedley всё ещё запускает настоящий графический процесс Victoria 2, но **человеку не требуется управлять GUI**.&#x20;

## **3. Как сделать настоящие тесты событий и решений**

Для уровня B я бы создал собственный `vic2_test_bridge.dll`, который будет работать непосредственно внутри процесса игры с CreatineCore.

**Codex**

Редактирование скриптов, запуск тестов, анализ ошибок

**Python + pytest**

Тестовые сценарии, проверки, JSON-отчёты

**Named Pipe / IPC**

Передача запросов и результатов

**vic2_test_bridge.dll**

Безопасный вызов проверенных функций на игровом потоке

**Оригинальный движок Victoria 2**

CreatineCore + твой мод + тестовое сохранение

Это предлагаемая архитектура, а не готовый существующий продукт.

Я бы реализовал в первой версии только пять операций:

| Операция будущего API         | Результат                               |
| ----------------------------- | --------------------------------------- |
| `load_scenario(save)`         | Загружает исходное состояние            |
| `evaluate_decision(id, tag)`  | Проверяет `potential` и `allow`         |
| `execute_decision(id, tag)`   | Выполняет решение                       |
| `fire_event(id, tag, option)` | Вызывает событие и выбранный вариант    |
| `snapshot(tag)`               | Возвращает наблюдаемое состояние страны |

Для начала этого достаточно, чтобы проверять большой класс ошибок в событиях и решениях.

Например, целевой тест на Python мог бы выглядеть так:

```
def test_industrialization(vic2):    vic2.load_scenario("prussia_1850.v2")    assert vic2.evaluate_decision(        "industrial_reform", "PRU"    ) == {        "potential": True,        "allow": True,    }    before = vic2.snapshot("PRU")    vic2.execute_decision("industrial_reform", "PRU")    after = vic2.snapshot("PRU")    assert after["industrialization_flag"] is True    assert after["treasury"] < before["treasury"]
```

Это пример **желаемого интерфейса**, не код, который уже сейчас можно выполнить через CreatineCore.

### **На чём основывать реализацию**

Исследования уже описывают полезные внутренние границы движка:

- `CDecision` и его блоки `potential`, `allow`, `effect`;
- классы `CTrigger` и механизм их вычисления;
- путь выполнения выбранного варианта события;
- работу очереди игровых команд;
- загрузку сохранения и вход в игровую сессию.

Особенно важно, что решения AI не применяются непосредственно в момент проверки `potential`/`allow`: они сначала помещаются в очередь, а выполняются позднее. Аналогичные ограничения есть у выполнения вариантов событий. Поэтому лучше использовать штатные игровые механизмы, а не просто вызывать найденный адрес функции.&#x20;

## **4. Как сохранить старые сейвы**

Я бы разделял две цели:

**Прямая совместимость:** старое сохранение открывается и корректно продолжается с новым движком.

**Обратная совместимость:** сохранение, сделанное новым движком, можно снова открыть старой версией.

Тебе, вероятно, прежде всего нужна прямая совместимость. Обратная значительно сложнее и её нельзя автоматически считать обеспеченной.

| Изменение                                         | Риск для старых сейвов                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------ |
| Оптимизация памяти и вычислений                   | Низкий, если патч не затрагивает сохраняемое состояние                   |
| Исправления экономических ошибок                  | Обычно не требуют миграции формата, но могут изменить игровые результаты |
| Новая формула цен                                 | Ожидается продолжение со старых цен, но динамика рынка изменится         |
| Новые типы товаров, POP или провинции             | Высокий риск — затрагивают идентификаторы и структуру данных мира        |
| Удаление и переименование событий, решений, стран | Требует отдельной проверки ссылок и сохранённого состояния               |

Для совместимости я рекомендую **не менять состав и идентификаторы игровых сущностей** одновременно с патчами движка. Старые сейвы должны тестироваться с тем же содержимым мода, для которого были созданы, но с новой DLL-конфигурацией.

Тестовый набор должен включать раннее, среднее и позднее сохранения, в том числе сохранение с большой промышленностью, действующими войнами и активными событиями.

Для каждого исходного сейва:

- Проверить загрузку и отсутствие ошибок.
- Прокрутить один день и проверить критические значения.
- Прокрутить 30–90 дней без вмешательства человека.
- Сохранить результат в новый файл.
- Снова загрузить этот файл и продолжить симуляцию.

Особенно важно проверить формат нового сохранения, наличие стран и провинций, работоспособность фабрик, отсутствие пропавших армий, некорректных цен и отрицательных значений там, где они невозможны.

Нельзя считать два сейва эквивалентными только потому, что они открываются. Нужна хотя бы проверка семантических инвариантов, а не сравнение хешей целых файлов.

## **5. Как вести интеграцию в Git и не ломать сборку**

Я бы завёл четыре конфигурации, которые можно воспроизводить независимо.

| Профиль            | Содержимое                                                      | Назначение                                  |
| ------------------ | --------------------------------------------------------------- | ------------------------------------------- |
| `vanilla-baseline` | Исходная 3.04 + твой мод                                        | Эталон и старые сейвы                       |
| `cc-safe`          | Только выбранные исправления и проверенные ускорения            | Проверка производительности и совместимости |
| `cc-economy`       | `cc-safe` + новая формула цены                                  | Игровой баланс и экономические регрессии    |
| `cc-experimental`  | Дополнительная многопоточность, новые механики, тестовый bridge | Разработка и исследования                   |

Код мода, конфигурации INI, исходники `vic2_test_bridge.dll`, Python-тесты и сведения о версиях зависимостей нужно хранить в Git. Оригинальные игровые бинарники и ассеты — отдельно. Для CreatineCore зафиксируй commit GitHub, а не просто скачивай последнюю сборку при каждом запуске.

**Критерий принятия изменения:** сначала успешные статические проверки, затем загрузка старых сейвов, прохождение коротких тестов движка и только после этого длительные прогоны производительности. Изменения цен проверяются относительно `cc-safe`, а не относительно ванильной экономики, потому что результат заведомо должен отличаться.

Мой выбор для первой законченной версии:

**CreatineCore + консервативные оптимизации + процентное ценообразование + Victorian Tools + набор тестовых сохранений.**

Затем — Smedley CLI как отдельный прототип автоматизации и, после проверки его возможностей, собственный узкий bridge внутри основной сборки. Так ты довольно быстро получишь исправленную игру, а инструментальную часть сможешь развивать независимо, не рискуя своими сохранениями.
