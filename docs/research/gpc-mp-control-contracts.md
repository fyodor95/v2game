# Управление сетевой партией через штатные команды Victoria II

Дата: 15 ноября 2026 года. Статическое исследование `v2game.exe`, SHA-256 `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`. Использованы PE-образ и существующее `.work/creatinecore/game-disassembly.txt`. Игра, GUI и сборки не запускались, `.work` не изменялся. По результатам отдельно разрешено добавить кандидат заголовка адаптера, описанный в разделе 10. Адреса VA приведены для базы `00400000`; в адаптере использовать фактическую базу плюс RVA.

## Вывод

Управление ходом настоящей MP-партии без мыши и клавиатуры возможно через те же верхние методы `CInGameIdler`, которые вызывают кнопки `pause_bg`, `button_speedup` и `button_speeddown`. Эти методы создают обычные игровые команды и передают их в сетевую очередь. Их можно квалифицировать для CLI отдельно от запрещённых диагностических мутаций мира.

Текущий `Pause` моста использует подходящую верхнюю функцию, **но только при выполнении дополнительных MP-предусловий**. Её запасная ветка меняет локальную паузу. Текущий `MaximumSpeed` вызывает непосредственно `execute` команды и обходит сеть; разрешать его для MP нельзя. Для MP требуются отдельные асинхронные операции, которые не повторяют toggle, пока предыдущая команда ожидает обработки.

Вызов штатного сохранения сам по себе не создаёт сетевой барьер. Он пригоден как кандидат сохранения на host после подтверждённой общей паузы и проверки фазы исполнения, но необходим отдельный runtime-тест. Наличие сохранения и его успешная повторная загрузка в SP не доказывают этот MP-контракт.

## 1. Объекты и пределы разрешения

Режим и lifetime описаны в [gpc-multiplayer-contracts.md](gpc-multiplayer-contracts.md). Здесь подтверждены следующие связи:

| Объект/поле | Назначение и ограничение |
| --- | --- |
| `*(base+E588E8)` | Текущий `world` |
| `world+B24` | Текущий idler; проверять vtable `base+A0A34C` (`CInGameIdler`) |
| `idler+5C`, byte | Текущий MP-режим; для новой операции требуется ровно `1` |
| `idler+17E8`, затем `+12C` | Session manager; штатный accessor `VA 00651D10`, слот idler `+44` |
| `manager+34`, byte | Роль server. Значение `1` бывает также в SP; отдельно не является разрешением MP |
| `manager+38` | Очередь команд; её виртуальный слот `+18` принимает владение созданной командой |
| `manager+234`, byte | Флаг исполнения команды; для вызова управления из моста требуется `0` |
| `idler+1538`, byte | Наблюдаемое состояние паузы; штатный accessor `00647560`, слот `+158` |
| `world+B28`, int32 | Скорость `0..4`; меняется исполнением команды, а не обязательно при возврате UI-метода |
| `idler+1D18` | `CIngameLobby`; проверенная по RTTI vtable `00E0B310` |
| `*(idler+1D18)+E1`, byte | Условие активной сетевой ветки паузы; требуется ровно `1` |

`CIngameLobby` создаётся только в MP-ветке `00667DDB..00667E31`; в SP поле обнуляется в `00667E3A`. Его конструктор `00693DF0` первоначально обнуляет слово `+E0`, включая `+E1`. Метод игрового idler `0064EF50`, виртуальный слот `+108`, устанавливает `handler+E1=1` в `0064EFB4`. Поэтому просто загруженный игровой idler ещё недостаточен: до этого перехода нельзя вызывать pause как сетевую операцию. Само семантическое имя `session_started` для этого поля является интерпретацией; ветвление и момент записи подтверждены непосредственно. В структуре адаптера указатель называется `handler`, но тип объекта — именно `CIngameLobby`, не отдельный `CMultiplayerHandler`.

Для команд управления достаточно разрешить роль MP host `(mode=1, server=1)`. Pause технически допускает и client, но расширять контракт CLI на client для прохождения текущих тестов не требуется. Для клиента менять скорость запрещает сам движок. Дополнительно проверять соответствие очереди роли:

| Очередь | Vtable VA / RVA | `enqueue` VA / RVA, слот `+18` |
| --- | --- | --- |
| Host | `00E42728` / `00A42728` | `00A62EA0` / `00662EA0` |
| Client | `00E427C8` / `00A427C8` | `00A66B30` / `00666B30` |
| Локальная очередь | `00E42840` / `00A42840` | `00A68560` / `00668560` |

В `009B1215` session manager получает server=`1`; в `009B12DB` создаётся очередь через `00A60BD0`, её конструктор ставит vtable `00E42728`, а в `009B12EE` результат записывается в `manager+38`. Альтернативная ветка создаёт очередь `00A63830` с vtable `00E427C8` и записывает её в `009B1503`. Не считать локальную очередь подходящей только из-за доступного слота `+18`.

## 2. Кнопки действительно вызывают эти верхние методы

`pause_bg` — строка VA `00E1070C`; `button_speedup` — `00E10174`; `button_speeddown` — `00E10184`.

В конструкторе TopBar обработчик, хранящийся в `TopBar+29C`, связывается с функцией `00718D00` (`0070CF47`). Настройка интерфейса в `00713214..0071325E` присоединяет именно этот обработчик к `pause_bg`. `00718D00` получает idler из `TopBar+24` и переходит к его virtual slot `+15C`; таблица `CInGameIdler` содержит там `0066A2C0`.

Аналогично `TopBar+2C8` связывается с `00718CE0` (`0070CF8D`), а `00713288..007132DA` присоединяет его к `button_speedup`. Функция переходит к idler slot `+164 = 0066A0D0`. Обработчик `TopBar+270` связан с `00718CF0` (`0070CF01`) и `button_speeddown`; он переходит к slot `+168 = 0066A1B0`.

В `007132A3` проверяется `manager+34`: кнопки скорости получают рабочие обработчики только на server-ветке. На client-ветке они отключаются. Это независимое подтверждение ограничения роли, которое есть и внутри самих методов.

## 3. Pause: сетевой toggle и опасная локальная ветка

Контракт верхнего метода:

```cpp
// RVA 0x26A2C0, ECX = текущий CInGameIdler*, стековых аргументов нет, RET.
void (__thiscall* TogglePause)(void* idler);
```

Начало `0066A2E2..0066A2FA` требует одновременно:

1. `idler+1D18 != nullptr`;
2. `handler+E1 != 0`;
3. `idler+5C != 0`.

При их выполнении метод выделяет `0x5C` байт через игровой allocator, получает локальное имя/запись игрока через `0068B610(world)` и вызывает конструктор `0072CEF0(command, player_string, 0)`. Конструктор — `__stdcall`, `RET 0x0C`, результат `EAX=command`; vtable `00E1229C` соответствует RTTI `CPauseGame`, тип команды `0x430`. Поле `+58=0`, поле `+59` получает последний аргумент. Затем `0066A32E..0066A340` вызывает `manager+38 -> vt[+18](command)` и сразу выходит.

**Если хотя бы одно условие сетевой ветки не выполнено, метод доходит до `0066A374..0066A385` и непосредственно переключает `idler+1538`.** Поэтому одного режима MP недостаточно. CLI должен заранее отвергнуть переходное/неизвестное состояние, а не надеяться, что движок выберет нужную ветку.

`CPauseGame::execute`, VA `0072D010`, вызывает idler slot `+10C = 0064F040` с байтом `command+58` и строкой `command+3C`. При `command+59!=0` дополнительно проверяется уже установленная пауза. Обычная UI-команда имеет `+59=0`, поэтому это toggle, а не идемпотентное присваивание.

У `0064F040` есть собственные ограничения: проверка `idler+E9`, специальная пауза `idler+1539`, имя поставившего паузу игрока `idler+1D88` и счётчик `idler+1DB0`, первоначально `0x1E`. В `0064F0FD..0064F10C` сравниваются имена, прежде чем разрешить раннее снятие паузы другим игроком. Не изменять эти поля вручную и не обходить запрет повторной командой. Единицы времени счётчика в рамках данного исследования не квалифицированы.

Существующий мост `Pause(world, bool)` делает проверку состояния сразу после вызова и считает её подтверждением. Для SP это допустимое ранее проверенное поведение, для MP возврат из `TogglePause` означает только постановку команды. До обработки сети локальный `paused` ещё может иметь старое значение.

## 4. Скорость: вызывать генератор команды

| Действие | Верхний метод VA / RVA | Конструктор, размер, тип | Исполнение, которое нельзя вызывать из MP CLI напрямую |
| --- | --- | --- | --- |
| Повысить на один | `0066A0D0` / `0026A0D0` | `0072EE00`, `0x3C`, `0x330`, vtable `00E12454` | `0072EE90` / `0032EE90` |
| Понизить на один | `0066A1B0` / `0026A1B0` | `0072EF50`, `0x3C`, `0x331`, vtable `00E12494` | `0072EFE0` / `0032EFE0` |

Оба верхних метода: `void __thiscall(CInGameIdler*)`, без стековых аргументов, `RET`. Если mode ненулевой и `manager+34==0`, они выходят до выделения команды. Иначе создают команду и передают её той же очереди через `+18`. После enqueue вызывается обычный звук интерфейса; участие GUI не требуется.

Конструкторы имеют ABI `Command* __stdcall(Command* memory)`, `RET 4`. Предпочтительно использовать верхний метод, чтобы allocator, владение объектом, роль и остальные действия оставались штатными. Не создавать собственный сетевой пакет или новую разновидность команды.

`0072EE90` — virtual execute (`+18`) `CIncreaseGameSpeedCommand`. Весь его нормальный код читает `world+B28`, увеличивает и ограничивает результат диапазоном `0..4`, записывает его обратно; сетевой отправки в нём нет. Аналогичен `0072EFE0` для уменьшения. Поэтому нынешний `MaximumSpeed` моста обходил бы сетевой механизм.

MP-операция `set-speed(target)` должна отправлять только одно повышение/понижение, возвращать `pending`, затем после подтверждённого изменения вычислять следующий шаг. Не копировать существующий синхронный цикл из четырёх вызовов с требованием `actual == previous+1` сразу после каждого вызова. На границах `0/4` повторный запрос должен завершаться без enqueue, если цель уже достигнута.

## 5. Путь команды до передачи другим участникам

Общий слот `queue+18` является сетевым маршрутом, а не только локальным списком:

- Обычные конструкторы `CPauseGame`, `CIncreaseGameSpeedCommand`, `CDecreaseGameSpeedCommand` обнуляют `command+36`. Host enqueue `00A62EA0` выбирает ветку `+36==0`, задаёт порядковый номер `command+38` и помещает указатель в кольцевую очередь host `+9C` через `00A6A9F0` (вызов `00A62F45`). До возврата саму команду он не исполняет.
- Обработка host `00A61780` берёт эту очередь. В `00A61828..00A61836` создаётся локальная копия команды через её virtual `+34`, сохраняя порядковый номер. В `00A618B1..00A618B8` вызывается queue virtual `+70 = 00A63270`.
- `00A63270` извлекает исходную команду из кольца через `00A6AB10` (`00A633E9`), сериализует её тип через command virtual `+1C` и содержимое через virtual `+4` (`00A6347E..00A6349F`). Затем `00A63542` вызывает `00A8AC70(host_transport, 0, packet)`.
- `00A8AC70` обходит записи соединений размером `0xE8`, выбирает состояние соединения `4`, формирует отправку по каналу из аргумента и при необходимости фрагментирует пакет. Это статическое подтверждение рассылки, а не предположение по имени enqueue.
- Client enqueue `00A66B30` кладёт обычную команду в кольцо `+FC` через `00A6A9F0` (`00A66BBF`). Его virtual `+70 = 00A67DE0` извлекает её через `00A6AB10` (`00A67F76`), сериализует тип и содержимое (`00A68016..00A68035`), затем передаёт пакет серверу через `00A89F70` (`00A6809D`). Отдельная ветка немедленных команд `+36!=0` использует тот же transport, но обычные команды управления идут через кольцо.

Следовательно, для изменения pause/speed достаточно **одного** вызова верхнего метода на host. Вызывать его ещё и на client нельзя: это создаст вторую команду; для toggle результат может полностью отменить первое действие.

## 7. Сохранение после согласованной паузы

Существующий контракт описан в [save-research.md](../../tools/creatinecore/save-research.md):

```cpp
// RVA 0x275A80; ECX = EngineString* с виртуальным относительным именем;
// первый стековый аргумент = CInGameIdler*, RET 4.
void (__thiscall* Save)(EngineString* path, void* idler);
```

`save games/<basename>.v2` относится к перенаправленному пользовательскому каталогу; нельзя передавать абсолютный путь Windows. Входные 16 байт: `55 8B EC 6A FF 68 AC E3 B9 00 64 A1 00 00 00 00`. DWORD на смещении `+6` — перемещаемый адрес SEH handler `base+79E3AC`; при ASLR проверять его как указатель, а не жёстко сравнивать `00B9E3AC`.

В `00675B70..00675B85` функция сериализует глобальный `world` через virtual `+4`. В её прямом теле нет постановки `CPauseGame`, проверки роли, проверки MP или координации клиентов. Отсюда следует **отсутствие барьера**, а не доказанная чистота всех вызываемых сериализаторов.

Функция после записи вызывает `0066EEE0`, который открывает/закрывает игровое меню. Обычные ветки автоматической паузы при открытии (`0066EF35`) и снятия паузы при закрытии (`0066F1EF`) отдельно проверяют `idler+5C==0`, то есть не должны менять паузу MP. Но в `0066EFFB..0066F027` есть отдельная ветка закрытия дополнительного окна с вызовом pause без такой непосредственной проверки. Поэтому не объявлять весь Save чистым чтением и не квалифицировать произвольные сочетания открытых окон по одной успешной записи. Для первого стенда использовать обычную кампанию без дополнительных открытых окон и фиксировать, что save не поставил новую pause-команду.

Минимальный контракт будущего `mp-save`:

1. Только owner thread, точный текущий `CInGameIdler`, активная MP-сессия, `manager.server=1`, `manager.executing=0`. На client отказ до любых побочных действий.
2. В оркестраторе запретить новые действия обоих участников, дождаться ранее отправленных управляющих команд, подтвердить pause на обоих процессах, одинаковые raw date и повторно стабильные снимки. Только `host.paused=true` недостаточно.
3. Зафиксировать перед записью date, paused, speed, native RNG diagnostics и GPC persisted state на обоих участниках. Вызвать Save ровно один раз на host в его изолированном userdir.
4. Подтвердить завершение файла, затем повторить наблюдения обоих участников. Изменение date, pause, GPC или RNG требует разбора и не считается успешной квалификацией. Не исправлять расхождение локальной записью в память.
5. Проверить содержимое сейва независимым oracle и затем восстановление новой MP-парой. Локальные персональные/UI-поля сейва не сравнивать побайтово с клиентским процессом.

Отдельный вызов Save на client в таком протоколе не нужен. Native world serializer, его возможные изменения кэшей и RNG, а также сетевой timeout при длительной записи требуют runtime-наблюдений. В данном отчёте эти проверки не выполнены.

## 8. Предлагаемый протокол CLI и проверка без GUI

Существующий запрет локальных мутаций в MP оставить. Добавить отдельные операции штатного сетевого управления, чтобы `event`, `decision`, локальный `advance`, `--auto-events` и диагностический запуск GPC не получили разрешение вместе с pause/speed.

Для `mp-pause(target)` проверять текущее наблюдаемое состояние. Если оно уже соответствует цели и нет незавершённого запроса, команда не нужна. Иначе поставить один toggle через `0066A2C0`, вернуть идентификатор операции и состояние `pending`. Опрос читает состояние, но повторно toggle не отправляет. Повтор того же request ID возвращает прежнюю операцию. Конкурирующий запрос, смена сессии, потеря клиента или timeout завершаются явным отказом; нельзя повторять отправку автоматически после неизвестного исхода.

Для `mp-speed(target)` использовать верхние методы `0066A0D0`/`0066A1B0` по одному шагу с подтверждением. Внешний оркестратор считает завершением согласованное состояние **обоих** участников, а не только `accepted` на host. Возврат нативного метода не является acknowledgment.

MP advance реализуется в оркестраторе: согласовать скорость, снять паузу штатной командой на host, наблюдать дату, после нужной даты отправить одну pause-команду и дождаться общей остановки. Из-за сетевой очереди допустимо остановиться позже запрошенной даты; сравнивать состояние по фактически достигнутой одинаковой дате. Не пытаться исправить overshoot локальной паузой/изменением даты и не обещать точное число дней без отдельного синхронизированного механизма.

Минимальная квалификация на двух настоящих участниках:

| Сценарий | Обязательные наблюдения |
| --- | --- |
| Host ставит/снимает паузу | Одна `CPauseGame` проходит host enqueue и исполняется на обоих; общий paused/date, нет локального fallback |
| Повтор request ID до подтверждения | Нет второй команды и обратного переключения |
| Все скорости `0..4`, затем обратно | Один command на шаг; одинаковая скорость на обоих; native RNG/GPC не меняются из-за управления на паузе |
| Client просит скорость/host-only save | Отказ до enqueue, записи или изменения состояния |
| MP ещё загружается (`handler+E1=0`) | Pause отвергнута до вызова верхнего метода; локальный fallback не исполнен |
| Pause поставлена другим участником/особой причиной | Сохраняются штатные ограничения; нет принудительной правки `1538/1539/1DB0` |
| Сохранение на общей паузе | Завершённый файл host; состояния обоих стабильны; после новой загрузки сохранён GPC seed/rng/lastday/passseq |
| Разрыв соединения при pending | Явный timeout/смена session, без автоматического повторного toggle |
| Продолжение кампании | Тот же набор baseline OOS-проверок, что у GUI-прогона, с раздельными вариантами исходного ядра / GPC disabled / GPC enabled |

Полезная диагностика квалификации — счётчик/журнал enqueue только типов `0x430`, `0x330`, `0x331` и их execute на обоих участниках. Наблюдательные hooks не должны создавать дополнительные команды, менять мир или RNG. Для принятия snapshot сравнивать завершённые одинаковые фазы, а не только календарную дату.

Переданный главным агентом результат существующего GUI-baseline — 86 дней, конечная raw date `60367224`. Это внешнее свидетельство текущей задачи, здесь повторно не проверялось и не доказывает работу нового CLI-маршрута. Его следует сохранить как отдельную контрольную точку и не смешивать с ещё не проведённой квалификацией.

## 9. Перехост

Отдельная атомарная сетевая команда «сохранить и перехостить» в рамках этого исследования не установлена. Практический маршрут без GUI: общая пауза → квалифицированный host save → остановка принадлежащих стенду процессов → новые host/client процессы → штатные методы host/join/load, исследуемые отдельно. Не выполнять локальный load только на одном участнике действующей сессии и не переносить `idler`, manager, pending request или роль из прежнего процесса.

Итог квалификации должен включать native RNG/GPC состояние после загрузки обоих участников и дальнейшие согласованные тики. Обычный SP reload не заменяет MP rehost. Этот отчёт не устанавливает ABI создания лобби и подключения: они намеренно оставлены независимому исследованию.

## 10. Реализованный кандидат адаптера

Добавлен [mp_control.h](../../tools/vic2test/native/mp_control.h), namespace `vic2_mp`. `Inspect(base)` возвращает `State` с адресами `world/idler/manager/queue/handler`, полями `mode`, `host`, `speed`, `paused`, `network_ready`, `executing`. `mode` допускает только `0/1`; неизвестные значения и несовпадение сигнатур дают `std::runtime_error` до нативного вызова. `host` читает `manager+0x34`, а не неподтверждённое поле `+0x31`.

`RequestPause(base, bool)` и `RequestSpeedStep(base, unsigned target)` возвращают `RequestResult {before, queued, expected_paused, expected_speed}`. Обе операции разрешены только для активного MP host. Первоначальный запрет `executing=1` снят после дополнительного исследования очереди (§11). Сохраняется запрет вызова в переходном состоянии `handler==nullptr`/`handler+E1==0`. Уже достигнутая цель даёт `queued=false`. Один запрос скорости отправляет максимум один шаг; `expected_speed` — результат этого шага, который может ещё отличаться от конечной цели.

Возврат `queued=true` означает завершение enqueue-вызова, а не исполнение команды. SEH-ошибка внутри нативного вызова даёт `E_MP_NATIVE_CALL` с неизвестным исходом; повторять такой вызов автоматически нельзя. Проверка owner thread, дедупликация request ID, единственный pending-запрос, acknowledgment обоих участников и очистка состояния при смене сессии остаются обязанностью вызывающего моста/оркестратора. Заголовок намеренно не содержит IPC, save, GUI-вызовов, сетевых пакетов собственной конструкции или локальных записей в мир.

Все 15 используемых последовательностей байт сравнили Python-скриптом с PE-образом: совпали. RTTI `00E0B310` также прочитано непосредственно: `.?AVCIngameLobby@@`. Компиляция и runtime-квалификация заголовка в рамках этого поручения не выполнялись; их проводит главный агент на текущей паре процессов.

## 11. `executing` и постановка управления в очередь

Дополнительное исследование выполнено после наблюдения главным агентом `E_MP_BUSY` при постановке паузы во время работающей MP-кампании. К этому моменту главный агент сообщил об успешном старте пары без GUI-ввода, подтверждённых обоими участниками шагах скорости `0 → 4`, снятии паузы и продвижении даты. Эти результаты не были повторены в рамках статического исследования; отказ `E_MP_BUSY` произошёл до нативного вызова.

`manager+0x234` означает исполнение уже извлечённой команды. В `009B0A74` поле получает `1` непосредственно перед вызовом `command virtual +18` (`009B0A83`), затем сбрасывается в `009B0A9C`. В другой ветке `009B0B1E` выставляет поле перед `command virtual +38` — проверкой допустимости; при успехе `009B0B39` вызывает `virtual +18`, а `009B0C0D` сбрасывает поле. Это не занятость producer-очереди и не переключатель немедленного исполнения новых команд.

Нормальная постановка `CPauseGame`, `CIncreaseGameSpeedCommand`, `CDecreaseGameSpeedCommand` в очередь не зависит от этого поля:

1. Верхние методы `0066A2C0`, `0066A0D0`, `0066A1B0` проверяют режим/роль и для паузы `CIngameLobby+E1`, но не читают `manager+234`. Их квалифицированные MP-ветки создают команду с `command+36==0` и вызывают queue virtual `+18`.
2. В host enqueue `00A62EA0` ветка выбирается только сравнением `command+36` в `00A62EDF`. Обычная ветка `00A62EE4..00A62F5E` задаёт sequence, вызывает ring push `00A6A9F0` в `00A62F45` и возвращается. Она не вызывает execute, drain или сериализатор команды и не читает `manager+234`.
3. `00A6A9F0` копирует значение указателя команды в слот блока в `00A6AACF..00A6AAD4`, отмечает занятый слот в `00A6AAE5` и публикует sequence в `00A6AAF0`. Указатель команды не используется для virtual call. Единственный virtual call этой функции — allocator ring в `00A6AA3A`. Конструктор host `00A60C9D` задаёт ring vtable `00E4279C`; его slot `+4 = 00A6A220` вычисляет размер блока и вызывает slot `+C = 00A6A1A0`, выделяющий память через IAT `00C8A594`.
4. Helpers `009C12D0` и `00A6B230` выполняют spin/wait по полям ring. В них нет world, manager, command execute или обработки сообщений окна. Drain и сетевое распространение идут по отдельному пути, описанному в §5.

Следовательно, для этих двух API постановки управления запрет `executing=1` избыточен. Допустимо снять **только** этот запрет в `RequireHost`, оставив `State.executing` для наблюдений. Все остальные условия сохраняются: проверенный owner thread, активный MP host, `CIngameLobby+E1==1`, подписи функций, ровно один pending-запрос и подтверждение результата обоими участниками. Верхняя speed-функция после enqueue воспроизводит звук UI, поэтому точный вывод — отсутствие немедленного исполнения новой игровой команды и изменения симуляции через неё; утверждение об отсутствии любых глобальных записей было бы неверным.

Доказательство не разрешает прямой вызов command execute, сериализацию/снимок незавершённого мира или произвольный вызов с другого потока. Оно также не доказывает безопасность рекурсивного входа в ещё не завершённый producer: ring имеет ожидания предыдущей публикации. Вызов из квалифицированного owner-thread Pump во время уже выполняющейся игровой команды не означает такой рекурсии. Проверки завершённой фазы для save/snapshot сохраняются отдельно. После изменения требуется runtime-повтор: запустить ход времени, поставить паузу из Pump при наблюдаемом `executing=1`, подтвердить один enqueue и согласованный результат пары, отсутствие OOS и дальнейшее согласованное продолжение. Отказ до enqueue и неизвестный исход после нативного вызова должны оставаться различимыми.
