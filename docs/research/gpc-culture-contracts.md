# Крупнейшая культура и POP: статические контракты Victoria II 3.04

Исследован `v2game.exe` с SHA-256
`62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`.
Основание: локальный `game-disassembly.txt` и закреплённые исходники CreatineCore.
Все адреса ниже — **VA при базе 0x400000**; RVA получается вычитанием базы.
Это статические доказательства; runtime-проверки данным исследованием не выполнялись.

## Найден штатный выбор крупнейшей культуры

`FUN_009692C0` (`RVA 0x5692C0`) получает в **EAX** указатель на агрегат
населения. Стековых аргументов нет, завершение обычным `ret`, результат в EAX —
указатель на объект культуры. Сохраняет EBX/ESI/EDI.

Доказательство алгоритма (`game-disassembly.txt:1739140`):

```text
009692C1 mov ebx,[01258A20]       ; количество культур
009692C9 mov edi,[eax+48]        ; массив uint32 населения по культуре
009692CC xor esi,esi            ; первоначальный победитель = 0
009692CE xor edx,edx            ; первоначальный максимум = 0
009692D0 xor eax,eax            ; индекс = 0
009692D6 mov ecx,[edi+eax*4]
009692D9 cmp ecx,edx
009692DB jbe 009692E1           ; unsigned: равенство победителя не меняет
009692DD mov edx,ecx
009692DF mov esi,eax
009692E1 inc eax
009692E2 cmp eax,ebx
009692E4 jb 009692D6
009692E6 mov eax,[012587E8]      ; менеджер культур
009692EB mov ecx,[eax+10]
009692EE sub ecx,[eax+0C]
009692F1 sar ecx,2              ; число объектов в vector<Culture*>
009692F4 cmp ecx,esi
009692F6 jle 00969302
009692F8 mov edx,[eax+0C]
009692FB mov eax,[edx+esi*4]     ; объект победителя
```

**Ничья:** выбирается наименьший индекс культуры в менеджере среди культур с
одинаковым максимальным значением. Порядок POP и адреса объектов при этом не
используются. При нулевом массиве результатом будет культура индекса 0; поэтому
механика обязана отдельно исключать провинции без положительного населения.
Нельзя приравнивать native ID 0 к отсутствию культуры.

Выбор по uint32-агрегату не доказывает отсутствие переполнения в экстремальных
сценариях. Новый расчёт должен суммировать POP в uint64 и проверять расхождение с
кэшем. Тихое принятие переполненного кэша не подходит.

## Привязка агрегата к провинции и настоящему trigger

Строка `pop_majority_culture` находится по VA `0xE1E644`. Регистрация в
`00C4F472..00C4F48E` присваивает ей token **0x881**.

`FUN_008F1910` — Evaluate соответствующего условия, thiscall, `ctx` на стеке,
`ret 4`. Сравнивает результат `FUN_009692C0` с культурой условия `[this+0x1C]`.
Области:

| Область | Источник агрегата | Вызов helper |
|---|---|---|
| Страна, `ctx+0xC != 0` | страна `+0x12E8` | `008F1937..008F193C` |
| Область/state, `ctx+0x18 != 0` | `province[ctx+0x18]+0x188` → state `+0xC8` | `008F1965..008F1970` |
| Провинция, `ctx+0x10 != 0` | провинция `+0x1A8` | `008F1997..008F199F` |

Таблица провинций берётся из `world=*[0x012588E8]`, затем `[world+0xACC]`.
Следовательно, готовый массив культур провинции находится по указателю
**`[province+0x1F0]`** (`0x1A8+0x48`).

Дополнительные независимые потребители:

- `008AD4D2..008AD4D8`: провинциальный текст подстановки вызывает helper с
  `province+0x1A8`, затем форматирует объект культуры через `00974C50`.
- `008E026A..008E0272`: культура провинциальной области также определяется
  этим helper; соседняя POP-ветка `008E027B..008E027E` читает `pop+0x6C`.
- `00969310` читает долю конкретной культуры из `aggregate+0x48` по `culture+8`,
  проверяя индекс против `*[0x01258A20]`.

## Идентификатор и техническое имя культуры

Менеджер культур — `*[0x012587E8]`; его vector объектов имеет начало `+0x0C`,
конец `+0x10` и ёмкость `+0x14`. В объекте культуры:

- `+0x08` — индекс в этом менеджере;
- `+0x18` — игровая строка технического имени (старый MSVC string ABI):
  длина относительно начала строки `+0x10`, capacity `+0x14`; при capacity
  меньше 16 байты inline, иначе первый DWORD содержит указатель.

Доказательства:

- `0055EC04..0055EC25`: при построении менеджера присваивает последовательный
  индекс в `[culture+8]`, увеличивает счётчик, регистрирует имя.
- `005611F0..00561220`: hash-регистрация берёт имя с `object+0x18`; сравнение
  в `004A2FB5..004A2FDD` использует то же поле и SSO-layout.
- `008E0295..008E02A7` использует `[culture+8]` как индекс массива культур;
  `00969320..00969332` повторяет этот контракт для агрегата.

Не принимать `culture+0xC` за индекс: там другой идентификатор, получаемый
из таблицы символов при конструировании (`00560BCF`). Для равенства культур
в рамках загруженной кампании допустимы указатели, для сортировки/снимков —
квалифицированный индекс и имя. Между загрузками указатели не сохранять.

## Итерация POP и численность

Закреплённый `CCore_AssimilateBlock.cpp` содержит действующую реализацию:

| Поле | Смещение / источник |
|---|---|
| Указатель на массив списков POP провинции | `[province+0x194]` |
| Число списков | `(poptype_manager.end-poptype_manager.begin)/4` |
| Менеджер типов POP | `*[gameBase+0xF1BB34]`, vector `+0xC..+0x10` |
| Размер записи списка на тип | 16 байт |
| Голова списка типа t | `[lists+t*16]` |
| Следующий POP | `[pop+0x27C]` |
| Численность POP | `int32 [pop+0x58]` |
| Провинция POP | `[pop+0x64]` |
| Тип POP | `[pop+0x68]` |
| Культура POP | `[pop+0x6C]` |
| Религия POP | `[pop+0x70]` |

Источники: константы строки 83, 107, 115–125; `AssimPopTypeCount()` и
`AssimFindMergeTarget()` строки 874–902. Native loader подтверждает size:
`009569CF..009569D5` передаёт `pop+0x58` числовому reader; культура записывается
в `pop+0x6C` в `00956ABB..00956AC8` после lookup по менеджеру.

Суммирование: каждый POP учитывать ровно один раз; отклонять отрицательный size,
проверять принадлежность провинции/типу, циклы списка и предел числа объектов;
аккумулировать в uint64. Несколько POP разных профессий одной культуры складываются.

## Необходимая runtime-квалификация

1. На неизменённой тестовой провинции сопоставить сырые POP, uint64 суммы,
   кэш `[province+0x1F0]`, native helper и trigger `pop_majority_culture`.
2. Сценарий 40/35/25; сценарий, где крупнейшая культура разделена между POP,
   а крупнейший единичный POP имеет другую культуру.
3. Равенство двух культур при противоположном порядке POP. Победитель должен
   оставаться культурой с меньшим manager index. Проверить то же после загрузки.
4. Провинции с нулевым населением исключаются расчётом независимо от fallback
   native helper к культуре индекса 0.
5. Установить фазу актуальности агрегата: после изменения населения и до/после
   штатного дневного обновления. Кэш не считать свежим только из-за совпадения даты.
6. В сетевой сессии сверить vector order, ID, имена и суммы на всех участниках.
   Лексикографический порядок имён не заменяет native manager order для ничьей.

В существующем чистом модуле ноль — sentinel. Поэтому адаптеру нужен явный
перевод `nativeCultureIndex + 1`, включая обратное преобразование для диагностики;
не пропускать настоящую культуру с native ID 0.
