# Нативный MP-драйвер без ввода мышью и клавиатурой

Исследование от 15 ноября 2026 года. Первоначальная часть получена статически, без запусков, GUI-действий, сборок, Git и изменений `.work` исследователем. Позднее добавлены результаты первого runtime-цикла главного агента, явно обозначенные ниже. Исследован текущий Victoria II: Heart of Darkness 3.04 x86, SHA-256 EXE `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`, через PE-байты и существующий `game-disassembly.txt`.

Все VA ниже соответствуют базе `00400000`; для выполнения требуется действительная база плюс RVA. Статические контракты требуют отдельной runtime-квалификации. Наличие работающей GUI-сессии и настоящего сетевого соединения не следует из возврата callback.

## Выбранный уровень управления

Реалистичный узкий драйвер может находить уже созданные контроллеры и элементы интерфейса, устанавливать текст через native text component и вызывать штатные observable signals. Мышь, клавиатура, `SendInput` и поиск пиксельных координат для этого не нужны. При этом игра продолжает инициализировать обычное окно, frontend, рендер и сетевой цикл; наличие отдельного headless-режима этим исследованием не установлено.

`tools/vic2test/native/bridge.cpp` уже содержит квалифицированные на SP элементы такого механизма:

- `FindControl(object, slot, name)` создаёт старую игровую строку и вызывает native virtual lookup.
- `Signal(control)` вызывает native press/release `009EE510`/`009EE550` с `EAX=control+0x54`.
- Capture constructor/destructor поддерживает актуальные `CFrontEnd` и frontend pointers.
- IPC-запрос передаётся на поток владельца. Вызывать контроллеры непосредственно из pipe thread нельзя.

Это не означает, что любой существующий CLI-вызов разрешён в MP. Особенно нельзя переиспользовать прямое `advance`, выполнение события/решения, изменение `world+0xB28` или автоматический выбор опций. Новый драйвер должен иметь отдельные команды с собственными predicates текущего frontend/lobby/MP-состояния.

## 1. Вход в MP и поиск контроллера

Имя настоящей кнопки главного меню в `interface/temp_frontend.gui` — `multi_player_button`. Штатный путь поиска повторяет существующий `open-single-player`:

```text
owner = актуальный CFrontEnd из существующего capture
panel = FindControl(*(owner+0x704), 0x6C, "mainmenu_panel")
button = FindControl(panel, 0x34, "multi_player_button")
Signal(button)
```

Существующий мост проверяет vtable `CFrontEnd = base+0xA13DBC`; RTTI этой таблицы действительно `.?AVCFrontEnd@@`. Префикс `open-multiplayer` здесь обозначает возможную будущую команду моста, а не уже существующий CLI-флаг игры.

Конструктор `CMultiplayerMenuView` — `00763520` (`RVA 00363520`, строка 1086257), vtable `00E14844` (`RVA 00A14844`). В его объекте:

| Поле | Наблюдаемое назначение |
|---|---|
| `+0x04` | Указатель на владеющий CFrontEnd |
| `+0x368` | Панель `multiplayer_menu` |
| `+0x36C` | Общий modal host/direct-connect |
| `+0x370` | Панель процесса подключения |

Вызывающий участок `0075A3EC` (строка 1075474) создаёт view; `0075A3FA..0075A400` сохраняет его в `[begin+0x10]`, то есть в **пятый элемент массива прямых view pointers**. Промежуточных holder objects здесь нет. В этой функции `EBX` указывает на secondary subobject `root+0x88`, а не на primary `CFrontEnd`. Конструктор `00754A30..00754A49` создаёт этот подобъект с vtable `00E13F5C`. Поэтому операнды `[ebx+0x6C4]` и `[ebx+0x6C8]` означают begin/end по **primary `root+0x74C/+0x750`**. Аналогично текущий индекс `[ebx+0x6D4]` из `00759A35` находится в primary `root+0x75C`.

Первый runtime-цикл главного агента подтвердил: у captured `CFrontEnd` root с RTTI `.?AVCFrontEnd@@` begin/end по `+0x74C/+0x750` ограничивают восемь прямых указателей; `array[3]` — frontend view с vtable `base+0xA14ED0`, `array[4]` — multiplayer view с vtable `base+0xA14844`. Поле `view+4` у обоих равно primary root. По `root+0x6C4/+0x6C8` находилось значение `0x44610000` (float 900), что опровергло первоначальную интерпретацию этих смещений как primary vector.

Это исправление первого квалификационного цикла: прежние утверждения о primary `+0x6C4/+0x6C8` и чтении `holder+0x10` были ошибочны. Гипотеза, что captured root надо заменить на `root+4`, также опровергнута RTTI и runtime-проверкой ownership. Primary root и отношение `frontend+4 == root`, используемое frontend adapter, остаются верными.

Драйвер проверяет границы массива, тип view и совпадение `view+4 == root`. Наличие view ещё не означает завершения асинхронного перехода: первый `mp-open` уже активировал настоящую кнопку и открыл MP, после чего ошибочный поиск по прежним смещениям вернул `E_NOT_READY`. Поэтому статус команды должен различать отправку перехода и готовность панели; ошибку обнаружения нельзя устранять повторной отправкой signal без проверки текущего состояния.

## 2. Host и direct join

Статически связаны кнопки, observer objects и callbacks:

| Кнопка на `view+0x368` | Observer в view | Callback VA | Действие |
|---|---|---|---|
| `host` | `+0xB0` | `00764B30` | Показывает host modal |
| `join` | `+0x100` | `007651F0` | Подключение к выбранной LAN-записи |
| `join_direct` | `+0x240` | `00766B80` | Показывает direct-IP modal |

Инициализация callbacks видна в `007635BD..007635D1`, `007635EB..007635F9`, `0076368B..00763699`. Конструктор observer glue `00768830` хранит владельца в `+4` и callback в `+8`.

Важное различие: участок `00763C90..00763EA2` относится к **destructor** и снимает observer-подписки. Его нельзя принимать за регистрацию. Для native observable `vt+0x04 = AddObserver`, `vt+0x08 = RemoveObserver`; это также явно зафиксировано в upstream `V2TechButton.cpp:661–663`.

Общий modal содержит edit box `edit` и кнопку `ok_host_button`. Один и тот же `ok_host_button` используется для разных действий: показать modal — недостаточно, show callback ещё переключает подписки. Драйверу следует нажимать найденный signal уже настроенного modal, а не вручную подменять observer.

Найдены оба подтверждающих обработчика:

| Режим | Callback VA/RVA | Контракт |
|---|---|---|
| Host confirm | `00767C30` / `00367C30` | `ECX=view`, стековых аргументов нет, `ret` |
| Direct join confirm | `00767140` / `00367140` | `ECX=view`, стековых аргументов нет, `ret` |

Host callback читает `edit` (`00767CB0..00767D28`), формирует штатную конфигурацию, создаёт session manager через `009AE5F0` (`00767F3A..00767F74`), передаёт его владельцу через virtual slot `+0x48` (`00767FC2..00767FCB`) и инициирует серверную очередь через её virtual method (`00767FCD..00767FE0`). Затем выставляет native состояние MP и frontend-переход (`00767FE2..00768032`). Это полноценный обычный путь игры, а не локальная запись controller vector.

Direct join callback читает то же `edit` (`00767188..007671A9`), сохраняет конфигурацию с неблокирующим клиентским признаком `0` (`007673B5..007673F5`) и вызывает `00765870` (`00767489`). Последняя функция переключает панель на подключение, создаёт manager из сохранённой конфигурации (`007658CA..00765939`) и вызывает queue connect method `vt+0x24` (`0076597E..00765996`). Поэтому ответ на команду должен означать «подключение начато», а завершение подтверждается последующим изменением frontend/lobby и составом участников.

Перед этими сигналами требуется квалифицированная установка и обратное чтение имени игрока и modal text. Text ABI исследован отдельным участником: edit lookup `panel.vt+0x40`, text component `control+0x54`, `SetText` через `vt+0x40`, `GetText` через `vt+0x4C`. Эти методы должны получать native GameString, а не современный `std::string`.

## 3. Выбор сохранения, страны и старт

В этой части нельзя считать SP helper `load-save` готовым MP-драйвером: он непосредственно записывает `frontend+0x590` и флаг `+0x5BC`, а сетевой путь ещё надо подтвердить на host/client. Предпочтителен настоящий action выбранного save row.

Согласованные результаты параллельного статического исследования:

- Save checkbox callback `00777DB0` получает `ECX=frontend`, один stack argument clicked checkbox и возвращается `ret 4`. Он разрешает save row, записывает basename в `frontend+0x590` и вызывает `00778080`. Поиск актуального row и точные readiness predicates ещё требуется квалифицировать.
- Clickable country row: constructor `00769020`, vtable `00E150CC`; `row+0x28 = packedTag`, `+0x2C = country index`, `+0x30 = frontend`. Callback `00769580` получает актуальный session manager через frontend и создаёт `CSetCountryControllerCommand` через `007297A0`, затем вызывает `session_manager+0x38` queue `vt+0x18`. Это правильный сетевой action, а не прямая запись `world+0xB60`.
- `play_button` на `*(frontend+0x278)` подписан на observer `frontend+0x1D8` в `0076ABCD..0076ABDD`; callback `00772300` устанавливается в `0076A51F`. Таким образом, `Signal(FindControl(*(frontend+0x278),0x34,"play_button"))` ведёт в настоящий play handler. Нельзя подменять его `007733A0`: это другой handler.

Эти адреса переданы главным агентом/параллельным исследователем и должны проверяться вместе с их полным отчётом и актуальными сигнатурами. До определения reallist/listbox row lookup и readiness checks **полный путь load/save/select/start ещё не квалифицирован**.

Signal не воспроизводит hit testing мыши и сам по себе не доказывает, что кнопка была enabled. Поэтому перед Start нельзя обходить готовность загрузки сохранения, выбор стран, состояние участников и штатные ограничения lobby. Нужны наблюдаемые состояния до вызова, затем одинаковая дата и список людей на обоих участниках после перехода.

## 4. Изменение скорости через настоящую очередь команд

В этой части найдена короткая полноценная цепочка до очереди.

`CTopBar` хранит своё окно в `+0x20`, idler-владельца в `+0x24`. В `0071327E..007132DA` builder получает session manager через idler и разрешает speed controls только при `manager+0x34 != 0`; иначе соответствующие кнопки переводятся в отключённое состояние.

Подписки:

- `button_speedup` → topbar observer `+0x2C8` → `00718CE0` → idler virtual slot `+0x164`.
- `button_speeddown` → topbar observer `+0x270` → `00718CF0` → idler virtual slot `+0x168`.

Callback addresses записываются в `0070CF01` и `0070CF8D`; forwarding stubs — строки 992678 и далее. У квалифицированного `CInGameIdler` (`vtable 00E0A34C`):

| Действие | Native method VA/RVA | ABI |
|---|---|---|
| Увеличить скорость | `0066A0D0` / `0026A0D0` | `__thiscall(idler)`, stack 0, `ret` |
| Уменьшить скорость | `0066A1B0` / `0026A1B0` | `__thiscall(idler)`, stack 0, `ret` |

Методы проверяют текущий mode `idler+0x5C` и в MP требуют `manager+0x34 != 0`. Они выделяют native command `0x3C` байта, вызывают конструкторы `0072EE00` / `0072EF50`, затем отправляют объект через `session_manager+0x38`, queue `vt+0x18` (`0066A132..0066A144`, `0066A212..0066A224`). Это обычные `CIncreaseGameSpeedCommand` / `CDecreaseGameSpeedCommand`.

Для будущего драйвера допустимый узкий кандидат — вызвать эти **action methods на host** после проверки idler/vtable, mode, роли и сигнатур. Это сохраняет обычную сетевую маршрутизацию, даже если физические UI controls не используются.

Нельзя вызывать `0072EE90` напрямую: это command Execute, который непосредственно увеличивает `world+0xB28`. Так делает старый SP helper `MaximumSpeed`; отправки через очередь в таком вызове нет.

## 5. Пауза

Topbar pause callback `00718D00` перенаправляет в idler virtual slot `+0x15C`. У текущего `CInGameIdler` это `0066A2C0` (`RVA 0026A2C0`, `__thiscall(idler)`, stack 0, `ret`).

В `0066A2E2..0066A2FA` выбирается сетевая ветка при одновременном выполнении:

```text
*(idler+0x1D18) != 0
*(*(idler+0x1D18)+0xE1) != 0
*(byte*)(idler+0x5C) != 0
```

В этой ветке выделяется `0x5C` байт, получается current player record через `0068B610(world)`, создаётся `CPauseGame` через `0072CEF0` и объект отправляется той же native queue (`0066A2FC..0066A340`). Конструктор имеет три stack arguments и `ret 0x0C`; третий boolean нельзя без дополнительного исследования называть desired pause: обычный UI здесь передаёт ноль.

**Если сетевые условия не выполнены, `0066A2C0` может перейти к локальному toggle `idler+0x1538` в `0066A374..0066A385`.** Поэтому MP-драйвер обязан предварительно подтвердить сетевые predicates и роль хоста, иначе сам факт вызова этого метода не докажет сетевой характер действия. Нужна проверка штатной паузы на обоих участниках и поведения при уже установленной паузе; нельзя циклически повторять toggle при неясном результате.

## 6. Минимальные будущие interfaces и квалификация

Статически обоснованы следующие формы внутренних function pointers, но не готовые exports игры:

```cpp
using IdlerAction = void (__thiscall*)(void* idler);
// Increase: base+0x26A0D0; Decrease: base+0x26A1B0.
// Pause: base+0x26A2C0 только после подтверждения сетевой ветки.

using MenuAction = void (__thiscall*)(void* multiplayerView);
// ShowHost: base+0x364B30; ShowDirectJoin: base+0x366B80.
// ConfirmHost: base+0x367C30; ConfirmDirectJoin: base+0x367140.
// Для modal предпочтительнее Signal реального ok_host_button,
// чтобы сохранить актуальные observer subscriptions.
```

Сначала реализуется read-only discovery/status: актуальные owner/view pointers, RTTI/vtable, тип активной панели, текстовые поля, mode/role, состав lobby, readiness, состояние подключения. Затем действия добавляются по одному и доказываются настоящим переходом обоих участников.

Квалификационная последовательность: открыть MP из главного меню; задать два разных player names; host с локальным save; direct join на изолированный host; выбрать две страны штатными row actions; дождаться готовности; вызвать настоящий Start; изменить скорость на host через очередь; поставить/снять паузу через подтверждённую network ветку; сохранить/перехостить штатным путём. Каждый ответ отличает `accepted/pending` от `completed`, а timeout с неизвестным результатом запрещает автоматическое повторение действия.

Текущий MP-mode `idler+0x5C=1` у обоих участников подтверждён главным агентом в параллельном baseline; данное исследование само их не запускало. Это подтверждает режим, но не квалифицирует перечисленные новые вызовы. Сетевая проверка не должна заменяться двумя независимыми SP-симуляциями или локальным продвижением дней.

## 7. Реализованный frontend adapter и уточнённые контракты

В `tools/vic2test/native/mp_frontend.h` добавлены `Inspect`, `SelectSave`,
`SelectCountry`, `Play`, `CanStartWaiting`, `StartWaiting`. Это квалификационный тестовый драйвер:
методы вызываются владельцем CLI-моста на его потоке, получают `base`, текущие
`frontend`/`mainMenu` или `idler` явно и не хранят игровых указателей между
запросами. Результат `queued=true` означает лишь возврат штатной отправки;
загрузку/смену страны/старт подтверждает последующий опрос обоих процессов.
Нативное исключение даёт неопределённый исход: автоматический повтор запрещён.

### Session manager и страна

У `CFrontEnd` native getter `00757700` возвращает
`[[mainMenu+0x1E8]+0x12C]`. Метод embedded interface `frontend+0x3C`,
`vt 00E14F60`, slot `+0x28` — `00775920`: он берёт owner из
`[ecx-0x38]`, затем tail-calls owner `vt+0x44`, то есть именно этот getter.
Это доказывает эквивалентность пути адаптера реальному country-row callback.

`007695F9..00769651` строит команду `007297A0` с аргументами:
`memory, newTag, newIndex, oldTag, oldIndex, manager+0x6C` и передаёт результат
в `[manager+0x38].vt+0x18`. Объект имеет размер `0x50`, vtable `00E11F3C`,
поля `+0x3C/+0x40/+0x44/+0x48/+0x4C` соответственно. На `00729842` —
`ret 0x18`: конструктор **`__stdcall` с шестью аргументами**, а не `__cdecl`.
Адаптер повторяет этот сетевой путь без локальной записи выбранной страны и
без необязательного перемещения камеры из начала row callback.

Подтверждение выбора: Execute `00729850` находит player record через
`0068B500(command+0x4C, world)`. В `00729CC4/00729CC7` он записывает новый tag/index
в record `+0x20/+0x24` на каждом участнике. Затем `00729CD3..00729CD9` сравнивает
local `manager+0x6C` с ID игрока команды; только для этого игрока
`00729DA9/00729DAF` обновляет `world+0xB5C/+0xB60`. Поэтому эти world-поля подходят
для последующего ACK локального запроса. Согласованность всех игроков проверяется
по списку `world+0x18`: record `+0x1C` player ID, `+0x20/+0x24` tag/index,
`+0x3C` next. В Execute есть ранние ветви отказа при занятой стране, поэтому
возврат enqueue нельзя приравнивать к применению.

Native allocator `00AAE9AF` вызывается как `__cdecl(size_t)`; ownership команды
передаётся штатной очереди. Проверяются объект и все его payload-поля до enqueue.
Неизвестный ABI или исключение требуют завершить тестовую сессию. Проверяются
действительные server/client queue vtables `00E42728`/`00E427C8` и методы enqueue
`00A62EA0`/`00A66B30`. В frontend разрешены обе роли; `SelectSave`/`Play` — хосту.

### Выбор сохранения

Реальный `bookmarks` window через root `frontend+0x278`, slot `0x6C`, содержит
`bookmarks_list`, slot `0x7C`. В `00777E8D..00777E9A` slot `0x2C` listbox
возвращает адрес list header; `*header` — первый node, `[node]` — row,
`[node+8]` — следующий node. Это не массив GUI-контролов. Обход ограничен 8192
узлами, повтор узла запрещён. Проверка формы списка выполняется до мутаций.

Save row создаётся конструктором `00769670`, caller `0076C896`; его vtable
`00E15190`, filename `row+0x28`, корневой control `row+0x20`. Bookmark row имеет
другую vtable `00E14F9C` и пропускается. Реальный checkbox получается через
root slot `0x48`, имя `save_game` (`00777F75..00777F88`). При совпадении filename
и единственности row адаптер вызывает `00777DB0(frontend, checkbox)`:
`__thiscall`, один stack argument, `ret 4` на `0077806F`.

Callback сначала создаёт штатную команду через `0072AE30` и enqueue, затем
обновляет selection/filename и вызывает `00778080`. Прямая запись filename или
`frontend+0x5BC` здесь не используется. Адаптер принимает только basename `.v2`,
не файловый путь. Если сейв не представлен реальным списком, возвращается отказ.

### Два отдельных старта

Frontend `play_button` вызывается через `FindControl([frontend+0x278],0x34,...)`
и `Signal`. В `0076ABCD` кнопка подписывается на observer `frontend+0x1D8`,
callback `00772300`. Условный указатель `frontend+0x5C0` берётся из game config
`+0x130` в `0076B4E9..0076B50C`; это не основной manager `config+0x12C`.
Его ненулевое значение не навязывается как обязательный признак MP.

После загрузки создаётся отдельный `CIngameLobby`: конструктор `00693DF0`,
vtable `00E0B310`, pointer `idler+0x1D18` (`00667E14..00667E26`). Его root
control находится в `lobby+0x34`, idler — `+0xC0`, manager — `+0xDC`.
Конструктор `00694879..0069489B` подписывает `start_button` на observer
`lobby+0xE8`, callback `00697F20`. Callback строит `CStartGame` через
`0072A7B0`, enqueue через manager queue и unregister своего listener.
Это штатная сетевая команда, а не ручное снятие паузы.

`00697D93..00697E84` связывает готовность кнопки с `lobby+0xCC == 0` и ролью
server; состояние кнопки `3` означает недоступность. `StartWaiting` проверяет
текущий idler, mode, manager, observer owner/callback, pending count и состояние
реальной кнопки. При уже активном network flag `lobby+0xE1` возвращается
`already=true`, без повторной команды.

### Выполненные и оставшиеся проверки

Побайтно проверены все локальные сигнатуры адаптера по исходному точному EXE,
включая `ret 0x18` country constructor; адреса хранятся как RVA относительно
runtime `base`, релокируемые абсолютные операнды в сигнатуры не включены.
Код прочитан на ABI, lifetime и ownership: после `Signal`/enqueue игровые
указатели повторно не разыменовываются; новых локальных записей общей модели нет.
Сборка и runtime этих методов выполняются главным агентом отдельно.

В следующем runtime-цикле главный агент подтвердил всю последовательность без
действий рабочего стола: native Open → Host → direct Join → выбор `1891.v2` →
выбор AUS/NGF → Play. Оба участника перешли в настоящий `InGame` с mode MP=1 и
разными ролями host/client. Первый вызов `mp-ready` был отклонён до enqueue как
`E_MP_NOT_READY`; после стабилизации он вернул `queued=true`, а последующий опрос
обоих участников показал `network_ready=true`. Это подтверждает обычный промежуток
готовности между созданием кампании и возможностью Start, а не необходимость
ручного обновления GUI скрытого окна.

Для устойчивого bootstrap добавлен только read-only `CanStartWaiting(base,idler)`:
проверяются актуальный MP host, отсутствие исполнения команды, текущий lobby,
`network_ready==false`, его owner/manager/observer, `lobby+0xCC==0` и доступность
реального `start_button`. Метод не вызывает GUI Update, Signal или enqueue.
Контроллер ожидает этот predicate опросом, затем один раз отправляет Start и
отдельно ожидает `network_ready` на обоих. Сам mutator `StartWaiting` не изменён.
Проверки дальнейшего продвижения, rehost и отказов остаются отдельными критериями.
