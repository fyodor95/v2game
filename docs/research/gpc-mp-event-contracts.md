# Выбор опций событий в MP без графического ввода

Дата: 15 ноября 2026 года. Исследованы PE-образ `v2game.exe`, SHA-256 `62d48c204364dd706584777c2e2b3c7ab3c5f1dd0170872554943575d53d6648`, существующее `.work/creatinecore/game-disassembly.txt`, мост и адаптер уведомлений GPC. Игра, GUI, Git и сборки не запускались; `.work` не изменялся. Добавлен только кандидат `mp_events.h` и этот отчёт. Runtime-квалификация остаётся отдельным этапом.

Все VA ниже рассчитаны для базы `00400000`; в исполняемом адаптере использовать actual base + RVA. Упомянутый в переписке `4AE150` — **RVA**; действительная VA callback — `008AE150`.

## 1. Доказанный маршрут кнопки

`CEventWindow` имеет vtable `00E2CDB8`, имя RTTI `.?AVCEventWindow@@`. Конструктор — `008A8F30`, возвращает `EAX=popup`, `RET 0x50`. Его аргументы находятся в стеке: указатель создаваемого объекта, `CEvent*`, затем `CEventScope` размером `0x48` по значению. Сам конструктор не является обычным `__thiscall` с объектом в ECX.

В `008A8F8C..008A8F96` конструктор создаёт встроенный observer:

```text
popup+5C = 00E2CDD4       ; vtable CButtonObserverGlue<CEventWindow>
popup+60 = popup          ; владелец
popup+64 = 008AE150       ; штатный callback выбора опции
```

Для каждой опции конструктор создаёт кнопку и добавляет этот observer к её observable `button+54`: `008AA118..008AA128` для одной ветки интерфейса, `008AB031..008AB041` для другой. Указатели тех же кнопок добавляются в список `popup+B4/B8/BC` в исходном порядке опций. Это не указатели на объекты мира.

Callback имеет ABI:

```cpp
// RVA 0x4AE150; ECX = CEventWindow*, стековых аргументов нет, RET.
void (__thiscall* SelectEventOption)(void* popup);
```

Он выполняет следующие действия:

1. Проверяет `popup+58 != 0`.
2. Проходит список кнопок от `popup+B4` по `node+8`, считая индекс с нуля. В `008AE190..008AE199` выбирает первую кнопку, у которой byte `button+38 != 0`.
3. Выделяет `0xB0` байт игровым allocator, копирует scope из `popup+10` штатным `008A88D0`, передаёт событие `popup+0C` и выбранный индекс конструктору `00907D40`.
4. Через `popup+8 -> vt[+44]` получает session manager, затем вызывает `manager+38 -> vt[+18](command)` в `008AE1F6..008AE209`.
5. После возврата enqueue записывает `popup+58=0`, `popup+CC=1`. Это закрытие локального интерфейса, а не acknowledgment исполнения эффекта на остальных участниках.

Конструктор `00907D40` создаёт **`CSelectEventOptionCommand`**, подтверждено RTTI таблицы `00E333BC`. Его тип `0x3E4`, поле выбранного индекса `command+64`, встроенный scope `command+68`. ABI: стек `command*`, `event*`, scope по значению `0x48`, индекс; `RET 0x54`. Название `CEventOptionAction` не подтверждено этим образом: точное имя создаваемой сетевой команды — `CSelectEventOptionCommand`.

Новый адаптер вызывает callback, не конструктор команды и не её `execute` напрямую.

## 2. Почему команда действительно идёт по сети

`00907DA6` обнуляет `command+36`, как конструкторы обычных pause/speed-команд. В дальнейшем используется тот же подтверждённый маршрут очереди из [gpc-mp-control-contracts.md](gpc-mp-control-contracts.md):

- На host `queue.vtable=00E42728`, `enqueue=00A62EA0`, команда попадает в кольцо `queue+9C`; drain `00A63270` сериализует её и рассылает через `00A8AC70`.
- На client `queue.vtable=00E427C8`, `enqueue=00A66B30`, кольцо `queue+FC`; drain `00A67DE0` сериализует её и отправляет host через `00A89F70`.
- Сериализация использует virtual command `+1C` и `+4`; локальная копия создаётся через virtual `+34`. Для `CSelectEventOptionCommand` таблица содержит `execute=00907E00`, `type=00908DA0`, `copy=00908ED0`, `validate=00908FD0`.

Следовательно, **выбор делает только участник, которому принадлежит окно**. Это может быть host или client. Повторный выбор того же события на другом участнике создал бы вторую команду; оркестратор не должен дублировать его на обеих машинах.

Прямой вызов `00907E00` запрещён этому адаптеру. Игровой эффект исполняется только после прохождения штатного маршрута команды. Автоматическое открытие/запуск нового события, изменение корок, RNG или других данных мира при выборе не выполняются.

## 3. Получатель и canonical scope

Конструктор `008A8F30` читает country index из копии scope (`[ebp+1C]`), разрешает объект через country table `012587E4` и сохраняет `country+CDC` в `popup+8`. Поэтому для окна локального игрока можно проверить одновременно:

| Поле | Требуемое значение |
| --- | --- |
| `world+B60` | Переданный `localcountry`, то есть **числовой индекс**, не адрес объекта |
| `country_table[localcountry]+20` | Тот же индекс |
| `country+1C`, `world+B5C`, `popup+18` | Один packed tag |
| `popup+1C` | Тот же country index |
| `country+CDC`, `popup+8` | Текущий `world+B24` (`CInGameIdler`) |
| `popup+10` | Vtable scope `base+A2C904` |
| `popup+34` | Ровно `popup+10`, self embedded scope |
| `popup+20` | `0` для поддерживаемого здесь странового события |

`008A88D0` — копирование scope. Оно копирует self pointer `+24` буквально, поэтому промежуточная копия может содержать адрес предыдущего scope. Нужные долговечные объекты **исправляет сам движок**:

- В `008A9062` конструктор окна записывает `popup+34 = popup+10`.
- В `00907E68..00907E75` исполнение команды записывает `command+8C = command+68` до выполнения игрового эффекта.

Это нормальные контракты движка. Новый адаптер проверяет canonical self окна, но **не переписывает его** и не трогает self созданной команды. Старый обход `*(eventPopup+0x34)=eventPopup+0x10` из тестового CLI не нужен для настоящего нативного уведомления и не переносится в MP.

## 4. Где брать действительно живые окна

После создания окна `CEvent::run` в `008A8476` вызывает `008A8F30`, затем в `008A8494` передаёт результат в `006480E0` при `ESI=current_idler`.

`006480E0` регистрирует объект в базовом списке idler:

```text
idler+60 = head
idler+64 = tail
idler+68 = count
node+00 = object
node+04 = previous
node+08 = next
node+0C = служебный byte
```

Пустые ссылки — `nullptr`, sentinel отсутствует. Метод сначала ищет такой же object, чтобы не вставлять повтор. Создание node и обновление `tail/count/head` видны в `0064810C..00648139`.

Это список разных объектов интерфейса; отбирать из него следует только `CEventWindow` с подходящими vtable, получателем и флагами `+58=1, +CC=0`. Страновые события других стран и провинциальные события не подходят адаптеру GPC. Требуются ограничение длины, проверка `previous`, `tail/count`, циклов и повторов.

Такой список решает две задачи: проверяет, что адрес из `popups[]` по-прежнему принадлежит живой текущей сессии, и позволяет найти нативное GPC-уведомление, если диагностический capture его пропустил. Это чтение штатного контейнера, без сканирования произвольной памяти и без создания новых окон.

Внутри самого popup список `B4/B8/BC` имеет тот же layout, но содержит кнопки. Его длина должна совпасть с числом указателей опций `event+B0..B4`. Обе ветки конструктора создают кнопки в порядке этого вектора. Observer-список кнопки начинается с `button+58`, next тоже `node+8`; он должен содержать `popup+5C`. Это дополнительно подтверждает, что byte `button+38`, который меняет адаптер, принадлежит кнопке именно этого события.

## 5. Проверка CapturePopup: сдвиги корректны

Текущий naked hook моста делает `pushfd`, `pushad`, затем читает `[esp+2C]`, делает `push`, ещё раз читает `[esp+2C]` и вызывает `CapturePopup(object,event)`.

Если `S` — ESP на входе в конструктор:

```text
[S+00] return address
[S+04] popup
[S+08] event
[S+0C] начало scope
```

После `pushfd + pushad` текущий ESP равен `S-0x24`. Первая загрузка `[esp+2C]` читает `S+8`, то есть event. После его `push` ESP равен `S-0x28`; вторая загрузка `[esp+2C]` читает `S+4`, то есть popup. Порядок аргументов для `__stdcall CapturePopup(object,event)` правильный. Украденные пять байт `55 8B EC 6A FF` состоят из целых инструкций; trampoline продолжает с `008A8F35`.

Hook вызывается **до тела конструктора**. В этот момент новый object ещё не обязан иметь vtable, active flags и готовый scope. Capture поэтому может только запомнить адрес/аргументы; фильтровать его как завершённый `CEventWindow` прямо внутри такого hook нельзя. Во время последующего обычного `status` конструктор уже должен завершиться.

`CapturePopup` добавляет object в `popups[]` независимо от `requestedEventId`; это поле ограничивает только отдельный `eventPopup`. Поэтому отсутствие CLI-запуска события не объясняет нулевой `ActivePopupCount`. Деструкторный hook установлен в правильный virtual slot `0`: исходная функция `008AB600` имеет ABI `void* __thiscall(object,unsigned flags)`, `RET 4`, и передаёт тот же object настоящему деструктору `008AB630`.

**Конкретная причина сообщения «GPC-окно видно, event_windows=0» по имеющейся статике не установлена.** Менять сдвиги hook на этом основании нельзя. Обычный и GPC-пути используют один constructor callsite `008A8476`; отдельного обходного конструктора в `notify_probe::Dispatch` нет. Сохранённый `runtime-first.log` подтверждает отправку уведомлений странам `25/63/76`, но не содержит дампа capture/родного списка в момент видимого окна; сам по себе нулевой счётчик для AI-получателей ожидаем.

Минимальная диагностика для точного объяснения расхождения:

1. В том же PID записать адрес/target detour `base+4A8F30`, SHA bridge DLL и идентификатор сессии, исключив старый артефакт или другой процесс.
2. Записать вход capture: object, event ID, текущий поток, длину `popups[]`. Отдельно записывать достижение предела `256`; текущая реализация после этого новые окна отбрасывает.
3. При завершённом уведомлении снять родной список `idler+60` и для совпавшего event ID записать address/vtable/58/CC/tag/index, наличие в `popups[]`.
4. Записать удаление этого адреса в `PopupDelete`. Если адрес есть в родном списке, но отсутствует в `popups[]`, исследовать capture/lifetime. Если адрес есть в обоих, но count нулевой, сравнить реальные фильтрующие поля и код загруженной DLL.

До этого результата правильно использовать проверенный родной список как источник живых объектов, а не объявлять предполагаемую причину доказанной. Исправление bridge hook здесь не выполнялось.

## 6. Реализованный кандидат `mp_events.h`

[mp_events.h](../../tools/vic2test/native/mp_events.h) использует guard из `mp_control.h`, дополнительно проверяет собственные сигнатуры и layout событий. Доступ разрешён и host, и client, но только для их собственного локального игрока, при активной MP-сессии и `manager.executing=0`.

API namespace `vic2_mp_events`:

```cpp
PopupInfo ValidatePopup(uint32_t base, uint32_t popup, unsigned localcountry);
std::vector<PopupInfo> List(uint32_t base, unsigned localcountry);
PickResult Pick(uint32_t base, uint32_t popup, unsigned optionIndex, unsigned localcountry);
```

`PopupInfo` содержит `popup`, `event`, `event_id`, `country`, `tag[4]`, `option_count`. `List` читает родной список и возвращает только ожидающие страновые окна своего игрока. `ValidatePopup` также требует наличия адреса в родном списке; адрес из завершённой сессии или закрытое окно отвергаются. `PickResult {before, option_index, queued}` означает постановку команды, без утверждения о завершении сетевого эффекта.

Все проверки — сигнатуры, список, получатель, scope, callback observer, диапазон опций — выполняются до первой записи. Затем адаптер выставляет только локальные `button+38` так, чтобы выбран был один требуемый индекс, и вызывает штатный callback. Успешный возврат дополнительно проверяется по ожидаемым `popup+58=0, +CC=1`. Scope, мир, command fields, RNG и очередь напрямую не изменяются.

Ошибка во время записей или callback оставляет неизвестный/частичный исход и возвращается как `E_MP_NATIVE_CALL`. Автоматический повтор запрещён. Не восстанавливать UI-байты вслепую после неизвестного исхода. Повторный запрос после успешного закрытия окна отвергается до callback.

Обязанности bridge/оркестратора:

- Выполнять методы на подтверждённом owner thread, блокировать повтор request ID и не выполнять действие в отравленной сессии.
- Выбирать popup по требуемым `event_id` и `tag`, предварительно прочитав `List`/`ValidatePopup`. При нескольких подходящих окнах вернуть неоднозначность, не нажимать произвольное. Не полагаться на старый `requestedEventId`, относящийся к CLI-запуску события.
- Повторно проверить совпадение ID/получателя и вызвать `Pick` в том же owner-thread dispatch без промежуточного ожидания/нового игрового тика. Сам `Pick` заново проверяет живое окно и текущую локальную страну.
- Не отправлять этот выбор на втором участнике; ждать штатного исполнения и наблюдать результат на обоих.
- Не расширять разрешение на существующие локальные `event`, `decision`, автоматический перебор опций или запуск GPC. Нужна отдельная команда выбора уже существующего окна.

## 7. Статическая проверка и оставшиеся испытания

Все **11** массивов сигнатур нового заголовка сравнены Python-скриптом непосредственно с PE: совпали. В частности:

| RVA | Длина | Назначение |
| --- | ---: | --- |
| `004AE150` | 9 | Пролог штатного callback |
| `004AE190` | 16 | Выбор по локальному `button+38` |
| `004AE1CE` | 27 | Копирование scope и создание команды |
| `004AE1F6` | 32 | Получение queue, enqueue и закрытие popup |
| `004A8F6A` | 34 | Связь country → idler, event, scope |
| `004A9062` | 7 | Canonical self окна |
| `00507E68` | 19 | Canonical self команды перед эффектом |
| `00507DA2` | 11 | Обычная команда `+36=0` |
| `002480E3` | 10 | Head родного списка объектов |
| `0024810C` | 12 | Layout node |
| `00248120` | 28 | Обновление tail/count/head |

Вход конструктора не проверяется как оригинальные пять байт: он уже перехвачен существующим мостом. Проверяются неизменённое тело, живые объекты и их связи. Новый detour не устанавливается.

Необходимая runtime-квалификация без GUI:

1. На двух настоящих участниках получить по одному обычному страновому событию и убедиться, что `List` согласуется с ранее работавшим capture. Отдельно получить уведомление GPC и сравнить родной список с `popups[]`.
2. Выбрать свою опцию на client; журнал должен показать ровно одну команду `0x3E4` в client queue и её штатное исполнение на обоих участниках. Затем аналогично проверить host.
3. Для события с двумя различимыми опциями проверить индекс `1`, чтобы тест не проходил случайно из-за выбора первой кнопки. Итог эффекта сравнить на одинаковой завершённой фазе обоих процессов.
4. Неверный localcountry, чужой tag, неверный event ID на уровне bridge, уже закрытый popup, неверный индекс, неканонический scope и повтор request ID должны дать отказ до callback/queue. Не портить память настоящего мира ради отрицательных тестов: layout-ошибки проверять отдельной фикстурой.
5. Уведомление GPC задержать на одном участнике. Корки и GPC persisted state должны быть согласованы ещё до подтверждения; выбор только закрывает уведомление и не запускает второй проход. Продолжение партии не должно создавать новый OOS.
6. После перехоста старые popup адреса и request IDs не используются; новый список привязан к новому idler.

Компиляция и перечисленные runtime-тесты в этом поручении не выполнялись. Закрытие окна само по себе не является доказательством корректной сетевой доставки; нужны журналы команды и состояние обоих участников.
